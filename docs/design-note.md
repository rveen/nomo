# Nomo — Design Note

**Status:** design sketch, nothing built
**Date:** 2026-07-30
**Purpose:** Replace SMath Studio with a web-based, unit-aware engineering worksheet application.

## The name

**Nomo** — from *nomogram*, the printed calculating chart engineers read answers off before there
were computers. It names the kind of instrument this is without promising a computer algebra
system, it reads the same in English and in Spanish, and it stays short enough to work as a crate
name, a CLI verb, and a file extension:

| | |
|---|---|
| Core crate | `nomo-core` |
| CLI | `nomo render report.nomo` |
| File extension | `.nomo` — long form, decided |
| Document footer | `Generated by Nomo 0.1` |

**Checked before committing publicly (2026-08-28):** `nomo-core`, `nomo-cli`, `nomo-wasm`,
`nomo-smath` and `nomo-math` are all free on crates.io; `nomo-math` is free on npm and PyPI;
`github.com/nomo-math` is available; and `nomo.tools`, `nomomath.dev`, `nomo-math.dev` and
`nomomath.org` are unregistered. The bare `nomo` crate is held by an unrelated templating library,
which does not matter — this workspace publishes only the prefixed crates.

---

## 1. Context

**Short term.** Recommend CalcpadCE to users; the portable Windows build deploys with no install
friction, and CalcpadCE already ships Linux packages (AppImage, `.deb`, `.rpm`, and an Arch
PKGBUILD) built from its Tauri desktop wrapper.

> **Action item for the trial:** have testers keep a running list of everything they could *not*
> express in CalcpadCE. That list is the real requirements spec for the long-term build, and it is
> more trustworthy than any up-front analysis.

**Long term.** Nomo: a web application with the functionality of CalcpadCE or EngineeringPaper.xyz
(EP), with a sound and solid engine; simplicity as the second objective.

**Not in scope.** A computer algebra system. Symbolic manipulation of unknowns is explicitly
dropped. SMath's own symbolic capability is modest, so this is a smaller concession than it looks —
but note that symbolic differentiation over a small AST is roughly a weekend of work if it turns
out to be needed, and can be added later without disturbing the architecture below.

## 2. Settled architecture

```
┌─────────────────────────────────────────────────────┐
│ Browser (static assets, offline-capable)            │
│                                                     │
│   Text editor  ──►  core engine (WASM)  ──►  render │
│   (CodeMirror)      parse → DAG → eval       (KaTeX)│
└─────────────────────────────────────────────────────┘
                          │
                   (optional, dumb)
                          ▼
              storage service: documents in,
              documents out. No computation.
```

- **Text syntax input**, not visual math editing. This is the single largest simplicity lever
  available. EP's ~7,000-line generated ANTLR parser plus ~2,600-line `LatexToSympy.ts` visitor
  exist *entirely* because it consumes LaTeX from a visual editor. A text syntax replaces that
  subsystem with a few hundred lines of Pratt parser.
- **Engine compiled to WASM, running client-side.** Static hosting, offline capability, no
  per-keystroke network round-trip, and no server-side execution of untrusted worksheets.
- **The backend stores and shares documents. It never computes.** EP gets this right: its
  Cloudflare Pages Function is under 300 lines and does nothing but save/load sheet blobs against
  a KV namespace. CalcpadCE gets it wrong: its server computes *everything* (convert, lint,
  highlight, definitions, prettify), which is why its `main` branch cannot be hosted at all — a
  startup loopback guard in `Program.cs` throws unless the bind address resolves to
  `localhost`/`127.0.0.0/8`/`::1`.
- **Rust preferred** for the core (Go acceptable; larger WASM output and a thinner ecosystem here).
- **One core crate, three build targets:** WASM for the browser, a native CLI for batch rendering
  and the golden-file test suite, and optionally the storage service.

A server-side compute model was considered and rejected. It would permanently entail sandboxing
untrusted worksheets (loops, macros, and file I/O amount to arbitrary code execution), timeouts and
memory caps, DoS surface, per-user session state, scaling, and latency on every lint. The soundest
backend for this domain is the one with almost nothing in it.

## 3. Decision: numeric model

**Requirement:** a worksheet must produce identical results across machines.

**Decision: IEEE 754 binary64, executed in WASM, with a vendored deterministic math library.
Not rationals, not fixed-point decimal.**

### Why this satisfies the reproducibility requirement

**Verified against the WebAssembly specification and design documents — see §12 for sources.**

The authoritative enumeration of what is nondeterministic in WebAssembly is the design repo's
`Nondeterminism.md`. It lists: feature-support variation, the external environment, shared-memory
concurrency, NaN bit patterns, NaN sign bits, relaxed SIMD, and resource exhaustion. **General
floating-point arithmetic does not appear on that list.** The spec's numerics section states that
"floating-point arithmetic follows the IEEE 754 standard" and that "all operators use
round-to-nearest ties-to-even, except where otherwise specified."

Float irreproducibility in practice comes from four places. WASM closes three:

| Source of drift | Status under WASM | Verified |
|---|---|---|
| x87 80-bit excess intermediate precision | Eliminated. Each arithmetic instruction is defined as one IEEE operation with one rounding, so there is no intermediate for an engine to widen | Yes (by construction — see caveat below) |
| Compiler contracting `a*b+c` into a fused multiply-add | Eliminated. The deterministic core has **no scalar FMA instruction at all**; fusion can only enter via relaxed SIMD, which is opt-in | Yes |
| Auto-vectorisation reordering reductions | Controlled. You define evaluation order in the language spec; do not enable relaxed SIMD | Yes |
| **Transcendental functions** (`sin`, `exp`, `ln`, `pow`) | **Not solved by WASM — this is the real problem** | Yes |

**Transcendentals are the whole risk.** Confirmed: WebAssembly defines *no* transcendental
instructions. Its complete floating-point instruction set is `fadd`, `fsub`, `fmul`, `fdiv`,
`fsqrt`, `fabs`, `fneg`, `fceil`, `ffloor`, `ftrunc`, `fnearest`, `fmin`, `fmax`, `fcopysign`, and
comparisons. Since IEEE 754 does not specify transcendentals either, every platform `libm` differs
in the last bits — almost certainly the actual cause of the drift CalcpadCE documents in
`DEVELOPER.md`, where rendered decimals must be compared *with tolerance* because "AVX2 CPU
extensions of different architectures/CPU manufacturers behave slightly different at the edge of
precision."

This is good news, because it makes the exposure a *build* decision rather than a platform lottery:

**Compile your own math library into the module. Never import the host's.** A pure-Rust `libm`
compiled into the WASM binary produces the same bits everywhere, because it is the same code
everywhere. Calling out to JavaScript's `Math.sin` or a platform `libm` reintroduces exactly the
nondeterminism you are trying to eliminate. Enforce this in CI by asserting the module's import list
contains no math functions.

### Avoid relaxed SIMD — specifically

`relaxed_madd` performs `(a * b) + c` with **single rounding on hardware with FMA support and double
rounding without it**. That is precisely the drift mechanism, promoted to an instruction. The
proposal is explicitly a trade of determinism for speed and is opt-in; do not enable it, and assert
its absence in CI.

### The NaN caveat, and how to close it

NaN nondeterminism is real: when an operator returns NaN the specific payload bits are
nondeterministic (constrained — a returned NaN may not have fraction bits set that were not set in
any input NaN, except the most significant fraction bit), and when an operator produces NaN from
non-NaN inputs the **sign bit** is nondeterministic too.

Two mitigations, use both:

1. **Normalise NaN at every boundary.** Never let payload or sign bits reach the document format,
   a golden file, or the renderer. In an engineering worksheet NaN should surface as a typed error
   value long before it becomes a bit pattern anyway.
2. **Target Wasm 3.0's deterministic execution profile.** Wasm 3.0 (completed 2025-09-17) added a
   profile that "specifies a deterministic default behavior for every instruction with otherwise
   non-deterministic results — currently, this includes floating-point operators and their generated
   NaN values and the aforementioned relaxed vector instructions." It was introduced for exactly
   this class of requirement ("blockchains, or replayable systems"). **Open question:** which
   engines actually implement the profile, and whether browser engines expose it — worth checking
   before depending on it. Treat mitigation 1 as the guarantee and this as belt-and-braces.

**One honest gap:** the spec does not contain a single quotable sentence saying "non-NaN
floating-point results are bit-identical across engines." The guarantee follows from the
construction (each instruction is one exactly-specified rounding, and arithmetic is absent from the
nondeterminism list) rather than from an explicit statement, and design issue
[#1385](https://github.com/WebAssembly/design/issues/1385) requesting that it be spelled out is
still open. The conclusion is sound; it is just assembled rather than quoted.

### Why not rationals

Exact for `+ - * /` and integer powers, and trivially deterministic — but they solve the easy half
of the problem and not the hard half. `sqrt(2)`, `π`, and every trig or log call are irrational, so
you fall back to floats for exactly the operations that caused the drift. Engineering worksheets are
dense with transcendentals (trigonometry for geometry, logs for decibels, exponentials for decay).
Denominators also grow without bound under repeated arithmetic, costing memory and speed.

Worth adding later as an **opt-in value type** alongside `Real` in the value tower, in the way
CalcpadCE has `RealValue`/`ComplexValue` under an `IScalarValue` interface. Not as the default.

### Why not fixed-point decimal

Fixed-point handles wide dynamic range badly, and engineering units span enormous ranges (nm to km,
Pa to GPa) in the same worksheet. Decimal *floating* point (IEEE 754 decimal128) would fix the range
problem but is slower, less supported, and still offers nothing for transcendentals. The motivating
use case for decimal arithmetic is financial exactness, which is not a requirement here — engineers
care about significant figures on *display* and about reproducibility, neither of which requires a
decimal radix internally.

### Consequences

1. **Decimal-aware display, binary internals.** Round to significant figures at render time.
2. **Define evaluation order in the language spec.** Sums and products evaluate left-to-right;
   no unordered reductions, no parallel evaluation in the engine.
3. **Assert bit-exact output in the test suite — no tolerance.** This inverts CalcpadCE's
   compromise: they need tolerance because they cannot guarantee determinism. You can, so any
   drift is a genuine bug rather than expected noise.
4. Forbid relaxed-SIMD and any host math import in the build. Worth enforcing in CI.

## 4. Decision: dimensions and units

Represent a dimension as an **exponent vector over base dimensions**; a named unit is a
`(factor, dimension)` pair derived from it. This gives real dimensional analysis rather than string
matching, and user-defined units fall out for free. CalcpadCE's shape — a `Unit` carried on the
value itself (`RealValue`, `ComplexValue`) — is right: unit consistency is then enforced by
arithmetic rather than by a separate checking pass that can disagree with evaluation.

**The trap: affine units.** °C, °F, and gauge pressures carry an offset, so they are not simply
scaled quantities. `20°C + 5°C` is meaningless; `20°C + 5 K` is fine. Decide *before writing the
operators* whether affine quantities are forbidden in arithmetic or carry an explicit flag that
operators consult — retrofitting this touches every operator. (Python's `pint` distinguishes
these explicitly and is worth studying as prior art; naive engines silently produce nonsense.)

**This is a live requirement, not a hypothetical:** `°F` appears in the real SMath corpus (§8.5), as
do imperial units throughout — `in` is the single most-used unit across all 54 worksheets. Any
importer that mishandles affine units will produce wrong numbers on real user files.

Same class of question, to be answered explicitly rather than by accident:

- Is `rad` dimensionless? What does `sin(2)` mean versus `sin(2 rad)`?
- Logarithmic units: dB, dBA, nepers, pH.
- Currency, if it appears in cost calculations — it has no dimensional relationship to anything.
- Whether users may declare new *base* dimensions (EP has a `customBaseUnits` config; CalcpadCE
  supports custom units).

## 5. Decision: evaluation returns a trace, not a value

**The engine's evaluation result must be an AST annotated with per-node values and units — not a
scalar.**

This is the decision most likely to cause a rewrite if deferred, because the entire reason these
tools exist is that they *show the work*:

```
V = π·r²·h = π·(5 cm)²·(12 cm) = 0.942 dm³
    ↑           ↑                  ↑
    symbolic    values substituted  result
```

Producing that line requires the original expression structure, each leaf's value and unit, and
the final result, all surviving to render time with source spans intact. An `eval(ast) -> Value`
signature cannot produce it. The renderer then walks the annotated tree in three modes.

Secondary benefit: it makes the golden-file suite far stronger, because a snapshotted *rendered
trace* pins down substitution, unit conversion, and formatting behaviour, not merely a final number.

## 6. Recalculation model

**Model the worksheet explicitly as a dependency DAG.** Build it, topologically sort it, and
evaluate only the dirty subgraph.

One structure buys deterministic top-to-bottom semantics, real incremental recalculation, cycle
detection that raises an error instead of hanging, and natural caching. Neither existing project
does this properly and both pay for it — EP's `solveSheet` takes the *entire sheet* as one JSON
blob, returns every result at once, and caches on that whole blob with a 100-entry LRU, which is a
workaround for not having a dependency graph.

**Requirement from the SMath corpus: the DAG cannot be built from document order alone.** SMath's `≡`
operator declares a *global* definition whose scope ignores position — verified by 39 cases in the
corpus where such a variable is consumed above its own definition (§8.2 finding 4). Any worksheet
imported from SMath may rely on this, so the model needs two declaration kinds: positional bindings
that resolve in reading order, and global bindings collected in a pre-pass and visible throughout.
Decide whether Nomo's own syntax exposes global definitions or only reconstructs them on import —
but the engine has to represent them either way.

## 7. Document format

- **Explicit version number from the first commit.** Migrations as pure functions, one golden-file
  test per format version.
- EP's `Sheet.ts` is the cautionary example: it is full of fields commented "early sheets did not
  have this property" because versioning was retrofitted. Its constraint — old sheets must always
  remain readable with no data loss — is the right constraint, adopted late.
- Keep the format independent of the engine's internal AST, so that engine refactors are not
  format-breaking changes.
- Plain text and diffable, if the syntax is the source of truth. This is a real advantage of the
  text-syntax decision: worksheets go in Git and review like code.
- **Extension: `.nomo`, long form — decided.** Because worksheets are plain text and Git-diffable,
  the extension is something people *read* in file listings and pull requests far more often than
  they type, and there is no DOS-era reason left to abbreviate. No `.shf`.

## 8. SMath importer

**Confirmed requirement.** Users hold libraries of existing `.sm` worksheets; without a migration
path, adoption fails regardless of engine quality.

### 8.1 Format, verified against real files

Everything in §8 is measured against a **54-worksheet corpus** — all 48 published SMath wiki
examples, spanning versions 0.82 to 0.98 — held in `corpora/nomo-corpus/` with its own `README.md`.
See §8.6 for what that corpus does and does not cover; the short version is that it is entirely
pre-1.x.

`.sm` files are XML (UTF-8 with BOM, CRLF). Structure — **this is the pre-0.88 shape only;
see §8.9, which supersedes it**:

```
<regions>
  <settings>          document identity (GUID + revision), calculation
                      settings, page/print model
  <region id left top width height ...>
      one of: <math> | <text> | <plot> | <picture> | <area>
```

**Math is a postfix (RPN) token stream, not source text.** This confirms the central design
assumption: **the importer is a stack reduction over `<e>` elements, not a parser.** There is no
grammar to write and SMath's visual math entry is entirely sidestepped.

```xml
<!-- Van := 230 V -->
<e type="operand">Van</e>
<e type="operand">230</e>
<e type="operand" style="unit">V</e>
<e type="operator" args="2">*</e>
<e type="operator" args="2">:</e>
```

`type` is one of `operand`, `operator`, `function`, `bracket`; `args` gives the arity, which is what
distinguishes unary from binary minus.

### 8.2 Findings that change the design

**1. Units are operands carrying `style="unit"`, attached by multiplication.** `230 V` is
`230`, `V`, `*`. Units are *also definable in-document* by assigning one unit to another —
`ElecEngExample.sm`
opens with `VA : W` and `var : W`, declaring apparent and reactive power as aliases of the watt. A
`preserve="true|false"` attribute governs display/conversion behaviour. So Nomo's unit system must
support user-declared units at document scope on day one; this is not an advanced feature.

**2. `=` regions carry SMath's own cached answer as an operand.** In `ling.sm`:

```xml
<e type="operand">Ling_rms_N</e>   <!-- variable    -->
<e type="operand">345.78</e>       <!-- STORED RESULT -->
<e type="operator" args="2">=</e>
```

Verified by recomputation: `Ling_rms_N ← 489/√2 = 345.78` ✓, and a second region evaluates
`√(k/M)/(2π)` to a stored `8` where the true value is 8.004 ✓.

**Superseded in part by §8.9:** this is the *older* of two mechanisms, and 247 is the count for
that one. From version 0.88 a stored answer lives in a `<result>` element instead, which brings the
total to 553.

**This makes every SMath worksheet a free regression fixture.** Import it, evaluate it in Nomo,
and compare against the answers SMath itself stored. That validates the importer *and* the engine
against a real corpus with no hand-written expectations. It is the single most valuable thing in
these files — build the harness around it early.

Caveat: stored results are rounded to the document's display `precision` (`2` in both samples), so
the comparison must round Nomo's result the same way rather than demanding full precision.

**3. Control flow is function application, not special syntax.** Observed as ordinary postfix
functions: `if` (arity 3), `for` (arity 3), `line` (arity 8 — a statement block), `range`, `el`
(element indexing, arity 2–3), `mat` (matrix literal, arity *n*+2), `sys` (plot series). The
importer handles them with the same stack reduction as arithmetic. Genuinely good news for scope.

**4. There are three assignment-like operators, and one of them is a global definition.** Counts
across the 54-file corpus (§8.6):

| Glyph | Count | Meaning |
|---|---|---|
| `←` | 1089 | positional assignment (older versions) |
| `:` | 697 | positional assignment (newer versions — same semantics, different spelling) |
| `≡` | 304 | **global definition — position-independent scope** |
| `=` | 247 | display/query, carrying the cached result (see finding 2) |

`←` and `:` are the same operation spelled differently across versions, so the importer needs a
per-version glyph table keyed off the `<?application version?>` instruction.

`≡` is different in kind. **Verified:** across the corpus there are 39 cases where a variable defined
with `≡` is used in a region *above* its own definition — for example, `Batchreactor.sm` uses `Cb` in
region 3 and defines it in region 4; `CEE2500Test02Problem[2].sm` uses `p1` in region 2 and defines
it in region 35. This is Mathcad's global-definition semantics: `≡` bindings are visible everywhere
regardless of position.

**Refined by §8.9:** this holds for `≡` at the *root* of a region. Nested inside an expression the
same glyph is an equality test, and 81 of the 304 uses are nested.

**Consequence for §6 (the dependency DAG):** the graph is *not* derivable from document order alone.
Global definitions must be collected in a pre-pass before positional evaluation begins, and Nomo's
document model needs to preserve the distinction — a positional assignment and a global definition
are different declarations, and collapsing them on import would silently change results.

**5. `bracket` elements are display hints.** Postfix is already unambiguous, so `<e type="bracket">`
exists to round-trip visual grouping. Semantically ignorable; useful only if you want to reproduce
the original layout.

**6. Everything else in a region.** `<picture>` embeds base64 PNG via `<raw format="png"
encoding="base64">`. `<area>` marks collapsible sections. `<plot type="2d" render="lines" scale_x
transpose_x ...>` is a postfix expression plus view state. `<pageModel>` carries paper size,
margins, print areas, and header/footer templates with `&[DATE]` / `&[PAGENUM]` placeholders.
Complex arithmetic is present too (`Re`, `Im`, `conj`, `arg`), so the value tower needs complex from
the start.

**7. Text fidelity is already lossy in the source.** Text regions are `<text lang>` → `<p bold
href>`, and in `ling.sm` words run together across what were clearly separate lines
("...Jan 2010requested acceleration profile..."). Line structure is lost or encoded outside `<p>`.
Do not expect clean prose out of text regions.

### 8.3 Region ordering: resolved

**Resolved, and in the simplest direction: read regions in file order.**

Across all 54 corpus files, spanning versions 0.82 through 0.98, three orderings coincide *without
exception*: the order regions appear in the XML, ascending `id`, and ascending (top, left) geometric
position. SMath evidently normalises region order on save, so `id` is not an independent creation
counter in the saved artifact.

This supersedes my earlier claim that geometry must be used to recover evaluation order — the
importer can simply iterate regions as written. **Keep a validation assert** that file order still
matches (top, left) and warn if a file ever violates it, since this is an empirical regularity across
one corpus rather than a documented guarantee.

Note that this resolves *positional* order only. Global definitions (`≡`, §8.2 finding 4) sit outside
positional order entirely and still require a pre-pass.

### 8.4 Constructs confirmed present in real worksheets

The gaps I previously flagged as untested are all exercised somewhere in the corpus. 176 distinct
function names appear; the ones that matter for scoping:

| Area | Functions observed |
|---|---|
| Indexing / structure | `el` (454 uses — the single most common function), `mat`, `matrix`, `augment`, `transpose`, `col`, `rows`, `cols`, `chunk`, `length` |
| Control flow | `line` (statement block), `for`, `while`, `if`, `range` |
| Numerics | `solve`, `diff`, `int`, `bisection`, `sum`, `min`, `max`, `dRound`, `Gamma` |
| Interpolation / lookup | `hlookup`, `cinterp` |
| Strings | `num2str`, `findstr`, `IsString`, `stack` |
| Financial | `pmt`, `fv`, `pv` |
| Drawing | `pgon`, `ellipse`, `Rot` |

**User-defined functions are serialised identically to built-ins.** `f`, `f1`, `f2`, `F`, `P`, `g`,
`y`, `yL`, `fSJ`, `fχ2`, `nasaT`, `hPP`, `A.P`, `UoM` all appear as `<e type="function">` exactly like
`sin` or `sqrt`. The XML carries no marker distinguishing them, so **the importer needs a registry of
SMath built-ins**; anything not in it is a user-defined function whose definition should appear in
some region of the same document. Treat a call with no matching definition as an explicit import
error rather than guessing.

Operators beyond arithmetic: comparisons (`<`, `>`, `≤`, `≥`, `≠`), logical `&` and `¬`, factorial
`!` (arity 1), and `±`. Three rare glyphs — `—` (6 uses), `|` (3), `†` (2) — remain unidentified and
should be looked at before the importer claims completeness.

### 8.5 Units in real worksheets

12 of 54 files use units, with 33 distinct symbols. The distribution is worth seeing because it
contradicts any assumption that engineering worksheets are SI-only:

```
in(73) mm(64) MPa(52) m(46) ft(40) kN(22) kip(20) ksi(18) cm(15) sec(14)
lbf(10) psi(6) %(6) °(5) VA(4) W(4) V(4) GPa(4) kg(4) var(3) A(3) ΔF(3)
Ω(2) BTU(2) lb(2) gal(2) min(2) °F(2) K(1) N(1) g.e(1) slug(1) s(1)
```

Three things follow. Imperial and US customary units (`in`, `ft`, `kip`, `ksi`, `psi`, `lbf`, `slug`,
`BTU`, `gal`) are not an afterthought — `in` is the *most common unit in the corpus*. **`°F` appears
in real files**, which makes the affine-unit decision in §4 a live requirement rather than a
hypothetical. And `%`, `ΔF`, `g.e` show users inventing their own unit-like symbols, consistent with
the in-document unit declaration found in §8.2.

**Superseded in part by §8.10 — read both.** The 1.x corpus is entirely metric (`m s ° N kN mm MPa cm
kg GPa Hz rad Pa g.e kph`), with no imperial unit and no `°F` anywhere. The two corpora do not merely
differ in emphasis; each is a near-complement of the other, so **neither predicts unit coverage for
the third corpus**. Take from this section the requirement — imperial and affine units must work —
not the ranking. One caution from §8.10: the identification rule stated here and in §8.7 item 12 is
wrong — `style="unit"` is a display style, and ten of the 1.x corpus's 25 such symbols are ordinary
variables, several of them the unknowns the worksheet solves for.

The in-document-declaration reading, by contrast, **holds and is now confirmed twice.** In
`Engine Heat Rejection Calcs.sm`, `ΔF ← 0.55555555555·K` declares the Fahrenheit degree interval;
in the 1.x corpus, `a.0 := 1·m` and `G.0 := 10·kN` declare length and force scales the worksheet
then works in. Both are the `VA : W` pattern of §8.2 finding 1 with a magnitude on the right.
Two of the three symbols cited above are not user inventions at all, though: `g.e` and `%` have no
defining region in the corpus and are SMath built-ins.

### 8.6 The corpus, and what it is not

All 48 examples from the [SMath wiki examples page](https://smath.com/wiki/Examples.ashx) were
downloaded and unpacked: **54 `.sm` files**, containing 2162 math regions, 1540 text regions, 99
embedded pictures, 49 plots, and **247 `=` display regions usable as test assertions** (§8.2) across
32 files. Every finding in §8.1–8.5 is measured against this set.

**It is not an up-to-date corpus.** Version distribution:

```
0.82: 3    0.88: 3    0.90: 2    0.94: 1    0.96: 1    0.98: 1
0.85: 32   0.89: 2    0.93: 4    0.95: 3    0.97: 2
```

Everything is pre-1.x, and the bulk (32 of 54) is 0.85 from around 2010. The format demonstrably
changed *within* this range — the positional-assignment glyph moved from `←` to `:` — so assume it
changed again on the way to 1.x. **Current-version files are still needed**, and the ones that matter
most are the worksheets your actual users hold, not the wiki's.

Two practical notes. The wiki serves these behind an ASP.NET cookie-detection redirect, so a fetch
without a cookie jar loops; `curl -c/-b` works, and `scripts/fetch-corpora.sh` does it.

**And these are third-party worksheets by named authors, published with no redistribution terms, so
they are not in this repository.** The second corpus (§8.12) is worse on this point rather than
better: it is Springer Nature book-companion material with no licence at all. Both are fetched on
demand and verified against the per-file hashes in `scripts/corpora/`, which is what lets an
MIT-licensed repository be measured against documents it may not redistribute — the provenance is
committed, the documents are not. `THIRD-PARTY.md` is the full statement.

Two further worksheets, an industrial resonant-converter design and an interlock-monitor design, are
cited throughout §8.19–§8.28 as "the converter worksheet" and "the interlock worksheet". They drove
much of the importer and they are no longer here: they were customer documents rather than this
project's to publish. Their measurements stand; `examples/llc.nomo` and `examples/interlock.nomo`
are clean-room worksheets written here to carry the same engine features.

**Revised 2026-08-26** against both corpora — 54 wiki worksheets at 0.82–0.98 and 60 mechanics
worksheets at 1.3–1.5. Item numbers are held stable because §8.9–§8.12 cite them; items whose
content changed are marked **[revised]** with a pointer to the measurement that changed them, and
items 26–34 are new. What was believed before each revision stays legible in §8.9–§8.12; this list
is the current one, and where the two disagree, this list wins.

**Reading the file**

1. XML, UTF-8 **with BOM** — 114 of 114 files across both corpora. **[revised]** Line endings are
   *not* a constant: the wiki corpus is CRLF in all 54 files, the mechanics corpus LF in all 60
   (plausibly git normalisation rather than an SMath change). Depend on neither; it is XML.
2. **[revised]** Read the version from the `<?application ... version="..."?>` processing
   instruction, but **for reporting only — never to decide behaviour.** Era detection is structural
   (item 27). Observed `progid` values include `SMath Studio`, `SMath Studio Desktop`,
   `SMath Solver` and `SMath Solver Enterprise`.
3. Iterate `<region>` elements **in file order**. Do not sort. Assert that file order still matches
   ascending (top, left) and warn if a file violates it (§8.3). **[revised]** Traverse **depth-first,
   pre-order**: from 0.88 an `<area>` contains the regions it collapses. 442 of the wiki corpus's
   3878 regions and 308 of the mechanics corpus's 4090 are nested (§8.9 finding 5).
4. **[revised]** Dispatch on the region's payload child. The types actually present across both
   corpora are `math`, `text`, `plot`, `picture`, `area`, `xyplot`, `mathcadblock`, `image`,
   `writer`, `comboboxlist`, `cflabel` — and both earlier versions of this list were incomplete
   (§8.10 finding 1, §8.11). Treat the list as open: an unrecognised payload is an
   unsupported-construct report, never a silent skip. That rule matters more than the enumeration.

**Reducing math**

5. Each `<math>` is a **postfix token stream**. Reduce with a stack; there is no parser. Verified
   across both eras: every one of the mechanics corpus's 2874 inputs reduces to exactly one node.
6. `args` is the arity — the *only* thing distinguishing unary from binary `-`. Never infer arity
   from the glyph.
7. `<e type="bracket">` is a display hint. Ignore semantically; retain only if reproducing layout.
8. **[revised]** Treat `<e type="function">` names against a **registry of built-ins**; anything
   unknown is user-defined and must have a defining region in the same document, and a call with no
   definition is a hard import error, not a guess. Scope it from measurement: 97 built-in and plugin
   names are called across the two corpora, the top 30 cover 91.5% of the 4375 call sites, and 25 of
   them appear in a single file (§8.12 Phase 3). The registry is not core-only — `description`,
   `FindRoot` and `norme` are plugin functions inside the top 30. **Resolution is document-scoped,
   not global:** 14 names are built-in in one worksheet and user-defined in another, and four of them
   — `diff`, `int`, `ln`, `log10` — are users *shadowing a built-in* with their own definition. A
   document-local definition wins.

**Assignment, definition and equality — the most important semantic distinctions**

9. `←` (older) and `:` (newer) are both **positional assignment**. Map via a per-version glyph table.
10. **[revised] `≡` dispatches on the shape of its left operand, not on its position.** At a region
    root, across both corpora: 136 uses have a **name** on the left — a global definition with
    position-independent scope, collected in a pre-pass; 67 have a **call `f(args)`** — a function
    definition; and **86 have an expression — a stated equation, written for the reader, that binds
    nothing.** (§8.2's "24 of the 54 corpus files" over-counts: 23 wiki files contain the glyph, but
    only **14** carry a root-level name-binding — in the other 9 every `≡` is a test or a stated
    equation. The requirement is unchanged; its blast radius is smaller than recorded.) Nested inside an expression, `≡` is equation construction for a solver (133 of 161
    mechanics uses) or a boolean test (the wiki corpus's dominant case). Collecting every `≡` as a
    binding invents 86 variables at root and 81 more nested (§8.9 finding 6, §8.10 finding 6, §8.12).
11. `=` is a **display/query** whose second operand is SMath's cached result. Do not import it as an
    equation. Extract the stored value as a test expectation (item 22).

**Units**

12. **[revised] Units are recognised by resolving the symbol, never by reading `style="unit"`.**
    The attribute is a *display style*: in the mechanics corpus ten of the 25 symbols carrying it are
    not built-in units, and eight are ordinary variables — several of them the unknowns the worksheet
    solves for. The same symbols appear styled in one file and unstyled in another (§8.10 finding 2).
    Units are still attached to a magnitude **by multiplication**.
13. Support **in-document unit declaration** — day-one scope, in both observed forms: the alias
    (`VA : W`, `var : W`) and the magnitude (`ΔF ← 0.5555·K`, `a.0 := 1·m`, `G.0 := 10·kN`).
14. Honour `preserve="true|false"`, which governs display/conversion behaviour of a unit.
15. Imperial and US customary units are first-class: `in` is the most-used unit in the wiki corpus,
    ahead of `mm` and `MPa`, and `°F` appears, so **affine-unit handling must be correct**.
16. **[revised]** Expect user-declared unit symbols (`ΔF`, `a.0`, `G.0`) — these are real
    declarations per item 13. Do *not* assume every unusual unit-styled symbol is one: `%` and `g.e`
    have no defining region and are built-ins, and the rest are item 12's styled variables.
    **[revised]** Unit coverage does not generalise between corpora — the wiki set is
    imperial-heavy, the mechanics set entirely metric with no `°F` at all. Take coverage from the
    target user's own files (§8.5, §8.10).

**Everything else in a region**

17. `<picture>` holds base64 PNG in `<raw format="png" encoding="base64">`.
18. **[revised]** `<plot>` is a postfix expression plus view state. `<xyplot>` (third-party X-Y Plot
    Region) is a fully declarative chart spec — axes, grid, traces, fonts — plus an ordinary postfix
    `<input>`, so the same reducer covers it.
19. **[revised]** `<settings>` carries document-level `precision`, `exponentialThreshold`,
    `fractions`, plus the page/print model. **There is no `<angle>` element in 1.x** — angles ride on
    `°`/`rad` unit operands — so do not require it. 1.x adds `significantDigitsMode`, `mixedNumbers`,
    `roundingMode` and `approximateEqualAccuracy`; `significantDigitsMode` reinterprets `precision`
    as significant digits rather than decimal places and must be read.
20. Text regions are lossy *in the source*: line structure is already lost inside `<p>`. Do not chase
    fidelity the input does not contain. **[revised]** `lang` is per region and a document may carry
    the same worksheet in three languages; which one an import keeps is an explicit policy, not a
    first-match.

**Validation, built in from the start**

21. Emit a **coverage report** per import: unsupported constructs, unknown functions, unknown units,
    counted and located. **[revised]** From 1.x, start it with the `<dependencies>`/`<assembly>`
    manifest — the file states which plugins it needs before a token is parsed.
22. **[revised]** Extract every stored answer as an assertion: **1339 numeric answers are available
    before Nomo computes anything** — 553 from the wiki corpus (247 as the second operand of `=`,
    306 as `<result action="numeric">`) and 786 from the CAS-free regions of the mechanics corpus.
    Read the display unit from the sibling `<contract>` (197 and 477 respectively) and round the way
    the *region* did — `decimalPlaces`, `trailingZeros`, `significantDigitsMode` — falling back to
    the document's `precision`. Exclude regions carrying an `error` attribute: those fail inside
    SMath itself and are not importer failures.
23. Never silently drop anything. An unsupported construct becomes a visible marker in the output
    document so a human reviewing the migration can see the gap.

**Known unknowns**

24. **[revised, largely resolved]** `†` is the **cross product** — 48 uses, a binary infix operator
    nested in expressions, read off moment sums `r † F` and a unit normal `e.z † e.t(t)`
    (§8.10 finding 5). `|` is **logical or** — all 3 uses sit in an `if` condition between two
    comparisons (§8.11). `—` remains open, but narrowed: all 6 uses have a function call on the left
    and that function's expanded form on the right, which reads as a **symbolic-evaluation display**
    rather than a binding — if so its right-hand sides are stored answers for item 22. Confirm
    against SMath before implementing; none of the three is implemented on a guess.
25. **[resolved]** The format did change between 0.98 and 1.x, and structurally (item 27). The
    successor question is whether it changed again after 1.5 — same answer as before: get the
    worksheets the target users hold.

**Added 2026-08-26**

26. **Be XML-namespace-aware.** 1.x wraps everything in
    `<worksheet xmlns="http://smath.info/schemas/worksheet/1.0">` where pre-1.x had a bare
    `<regions>` root. A reader that matches unqualified tag names finds **zero regions in all 60**
    1.x files — the same total-silence failure as reading only the top level of a nested document.
27. **Detect the era from structure, never the version string.** The question is whether a `<math>`
    contains an `<input>`. Version strings range from `0.85` to `1.5.0.9678` and the structural
    break at 0.88 does not align with anything nameable in them.
28. **Support all four assignment target forms**, measured across both corpora: a **name** (2544), a
    **call `f(args)`** — function definition (469), **`el(A, i, j)`** — indexed assignment (103), and
    **`mat(...)`** — destructuring a vector of names from one expression (31), which is how a solver
    result is unpacked.
29. **The value tower needs complex numbers and 3-vectors from the start.** `Re`, `Im`, `conj`, `arg`
    and an imaginary-unit operand `i` appear with units attached (`(1+2i)·Ω`, results stored in `VA`)
    and `Re` applies element-wise to matrices (§8.2 finding 6); `†` needs 3-vectors and cross product
    (item 24). Neither is an extension to add later.
30. **Identifier text is escaped.** Names may contain an escaped apostrophe as `\0027\`; unescape
    before resolving. The apostrophe is otherwise both a separator in plot property paths and prime
    notation in variable names (`φ'`, `x''.S`), told apart by position.
31. **Give plot property-path operands somewhere to land.** 159 operands across 23 files are names
    like `XYPlot'Traces#0'Name`, assigned from ordinary math regions to configure a plugin region.
    They reduce as plain identifiers, so nothing breaks — but the document model must represent the
    side-channel or the configuration is lost.
32. **Honour per-region evaluation flags**: `ignoreUnits="true"` switches dimensional checking off
    for that region (8 regions), and `error` marks a region that already fails inside SMath (14).
33. **CAS constructs are out of scope and emit markers, not errors** (§8.12): the Maxima surface
    (`Maxima`, `MaximaTakeover`/`Control`/`Define`, `assume`, `ratexpand`, `float`, `simp`, `Jacob`),
    the symbolic-solve idiom (`Solve`, `Assign`, `Unknowns`, `Clear`, `at`), and symbolic `diff`/`int`
    over undefined functions. This costs 7.7% of the mechanics corpus's math regions. Note that
    `solve` and `int` themselves are **numeric** — always 4-argument — and belong in the registry.
34. **`<result action="symbolic">` is provenance, never an assertion.** 164 of them exist; they
    record what SMath derived, which a no-CAS engine will not reproduce. Keep them for a human
    reviewing the migration; never feed them to item 22.

### 8.9 Corrections, from building the reader (2026-08-26)

Everything in §8.1–8.7 was measured by scanning the corpus for token streams. Writing a reader that
has to account for *every* element of *every* file turned up six things that scanning missed. They
are recorded here rather than edited invisibly into the sections above, so that what was believed at
each stage stays legible.

**1. The format has two eras, and they split at version 0.88.** This is the important one.

| | 0.82–0.85 (35 files) | 0.88–0.98 (19 files) |
|---|---|---|
| Math body | `<e>` directly under `<math>` | `<e>` under `<math><input>` |
| Stored answer | second operand of a binary `=` | `<result action="numeric">` |
| Display unit of an answer | inside the expression | `<contract>` |
| Collapsible sections | flat `<area>` marker | `<area>` *containing* the regions it hides |
| `=` operators present | 247 | **0** |

An importer written to §8.1's shape alone finds **no math at all** in 19 of 54 files, and reports a
clean import of an empty worksheet. Detect the era from structure — does a `<math>` contain an
`<input>`? — rather than from the version string, which ranges from `0.85` to `0.96.4909.6802`.

**2. There are 553 stored answers, not 247, across 51 of 54 files.** `<result action="numeric">`
accounts for 306 of them, and it is the richer form: a full postfix expression that can carry units
and complex values, where the older form is a bare rounded scalar. The oracle is more than twice the
size §8.2 claimed.

**3. `<contract>` carries the unit an answer is displayed in.** 197 of the 306 `<result>` elements
have one. Without reading it, a stored `96` compared against a computed `2.4384 m` looks like an
engine bug rather than inches, and the oracle would report false failures on exactly the
unit-carrying worksheets it is most needed for.

**4. Display rounding is per region, not only per document.** `<math>` carries `decimalPlaces` and
`trailingZeros` attributes that override the document's `precision`. Item 22's instruction to round
to the document precision before comparing is therefore not quite right: round to the region's, and
fall back to the document's.

**5. Regions nest.** From 0.88 an `<area>` contains the regions it collapses instead of marking
them. **442 of the corpus's 3878 regions are one or two levels down.** Reading only the top level
silently drops eleven per cent of the content of every worksheet using a collapsed section —
including math regions and their stored answers. Read depth-first, pre-order; that is both page
order and evaluation order.

**6. `≡` is a global definition only at the root of a region.** Nested inside an expression it is an
equality *test*, appearing next to `&`, `¬` and `|` in `if` conditions. 223 of the 304 uses are at a
root and 81 are nested. Treating the glyph as a binding wherever it appears invents 81 variables and
loses 81 conditions.

Two smaller notes. 97 text regions carry the same prose twice under different `lang` attributes, so
which language an import keeps is a policy decision someone has to make rather than a first-match.
And the corpus contains 199 distinct function names, not 176; the earlier figure counted the input
side only, which is in fact the right thing to count — `el` appears 817 times in all, but 454 times
in expressions a worksheet asks to be evaluated.

**What this does to the open question in §8.6 and §11.** The worry was whether the format changed
again between 0.98 and current 1.x. It is now known to have changed *structurally* once already,
within the corpus, in a way that breaks a naive reader completely rather than degrading it. That
makes the answer "assume it did" considerably stronger, and current-version worksheets correspondingly
more urgent.

**Resolved, partly.** Of the three unidentified operators in §8.4, `|` is almost certainly logical
**or** — every use sits between two comparisons in an `if` condition. `—` (U+2014) is a binding
operator: it is the root of its region in all six uses, with a name or a function call on its left,
in files that also use `←`; which of the two it is remains unknown. `†` is still unresolved. None of
the three is implemented on a guess; all three are reported.

### 8.10 The 1.x era, measured (2026-08-26)

§8.6 named current-version worksheets as the thing the corpus could not supply, and item 25 called
the 0.98→1.x question "the largest open risk to the importer". Both are now answered against a
second corpus: **Martin Kraska's worksheets for *Technische Mechanik mit SMath Studio*** (Springer,
ISBN 978-3-658-50591-2), held in `corpora/technical-mechanics-samples/`. 60 `.sm` files — 31 distinct
worksheets, 29 of them present in two editions (`Auflage 1` and `1st edition, trilingual
worksheets`). **Both are trilingual**, ger/eng/rus; they differ in emphasis, not language (§8.13). Versions **1.3.0.9126** (29 files), **1.4.0.9654** (29) and **1.5.0.9678** (2).

| | |
|---|---|
| Regions | 4090, of which 308 nested one level down (7.5%) |
| Math regions / postfix inputs | 2738 / 2874 |
| Stored results | **1051** — 877 `numeric`, 164 `symbolic`, 10 `none`; 477 numeric carry a `<contract>` |
| Text regions | 2848 (ger 1026, eng 917, rus 903, dut 2) |
| Distinct function names | 147 — 79 defined in-document, 68 not |

**The format did change again.** But before the damage list, the finding that matters most:

**0. The stack reduction survives 1.x intact. 2874 of 2874 postfix inputs reduce to exactly one
node** — no underflow, no residual stack, brackets included. The §8.1 bet that the importer is a
stack reduction rather than a parser holds across both eras. `xyplot` and `mathcadblock` regions
carry ordinary `<input>` streams too, so one reducer covers every math-bearing construct in the file.
And the oracle is larger than the whole wiki corpus: **877 numeric stored results across all 60
files**, against 553 across 54.

**1. The container is a different shape, and a pre-1.x reader sees an empty document.**

| | pre-1.x (§8.1, §8.9) | 1.3–1.5 |
|---|---|---|
| Root | `<regions>`, no namespace | `<worksheet xmlns="http://smath.info/schemas/worksheet/1.0">` |
| Plugin manifest | — | `<dependencies><assembly name= version=/>` |
| Result kinds | `numeric` | `numeric`, **`symbolic`**, `none` |
| Math annotations | — | `<description lang=>` child of `<math>` |
| Payload types | math/text/plot/picture/area | **+ `xyplot` (93, in 45 files), `mathcadblock` (6), `image` (1)** |

Every element is namespaced, so a non-namespace-aware reader finds **zero regions in all 60 files** —
the same total-silence failure as §8.9 finding 1, one era later. This is now the second structural
break inside the format's history; treat "assume it changed again" as standing policy, not caution.

`<mathcadblock seqop="sys">` is benign, a math region with a layout hint. `xyplot` is the third-party
X-Y Plot Region (JXCharts): a fully declarative chart spec — axes, grid, traces, fonts — plus a
postfix `<input>`. Easy to import, merely undescribed until now.

**2. Item 12 is wrong, and wrong in the silent direction. `style="unit"` is a display style, not a
semantic marker.** Of the 25 symbols carrying it, ten are not built-in units — and only two of those
ten are units at all. They split three ways, and only resolution tells them apart:

- **Genuine units** — `m`, `s`, `N`, `kN`, `MPa` and the rest of the metric set below.
- **In-document declarations**, exactly as §8.2 finding 1 describes: `a.0 := 1·m`, `G.0 := 10·kN`.
  These *are* units, and confirm that finding holds in 1.x.
- **Ordinary variables styled upright for looks.** `4.2.sm` has
  `F.A := mat(A.x, A.y, A.z, 3, 1)`, where `A.x/A.y/A.z` are the unknown reaction components the
  worksheet exists to solve for, and the same file later writes the answer back with
  `mat(S.1, S.2, S.3, A.x, A.y, A.z, 6, 1) := R.nu·N`. Also `S.1/S.2/S.3` (28 uses each), `b`, `n`.
  The styling is not even consistent for the same symbols: `4.3.sm` writes the identical
  `F.A := mat(A.x, A.y, A.z, 3, 1)` with the components left unstyled.

An importer following item 12 literally invents eight units *and* loses the unknowns the worksheets
solve for. **Recognise units by resolving the symbol, not by reading the attribute.**

That last example is a construct in its own right: **`mat(...)` on the left of `:` is a destructuring
assignment**, binding a whole vector of names at once from a solver result. The importer needs it, and
the document model needs a declaration form that binds several names from one expression.

The genuine units here are all metric — `m s ° N kN mm MPa cm kg GPa Hz rad Pa g.e kph` — the exact
inverse of the imperial-heavy distribution in §8.5, and with no `°F` anywhere. §8.5's conclusion is
unchanged, but note that neither corpus predicts the other: unit coverage has to come from users'
own files.

**3. Item 19 is out of date. There is no `<angle>` setting in 1.x.** `<calculation>` carries
`precision`, `exponentialThreshold`, `trailingZeros`, `significantDigitsMode`, `mixedNumbers`,
`roundingMode`, `approximateEqualAccuracy`, `fractions`. Angle handling rides on the `°`/`rad` unit
operands instead.

**4. `significantDigitsMode` refines §8.9 finding 4.** It appears 1279 times as a per-region `<math>`
attribute, alongside `decimalPlaces` (1138), and it flips `precision` from decimal places to
significant digits. The oracle must read both per region or it reports false failures. Other new
`<math>` attributes: `optimize`, `trailingZeros`, `matrixOptions`, `breaking`, `evaluate`, and two
worth special handling — **`ignoreUnits="true"`** (8 regions deliberately switch dimensional checking
off) and **`error`** (14 regions error inside SMath itself; they are not importer failures and must
not be counted as such).

**5. `†` is the cross product. Item 24 closes.** 48 uses across 10 files, and unlike `—` in §8.9 it
is *never* at a region root: 46 of the 48 sit inside a `+`, summing moment contributions, and 2 sit
directly under a `:`. It is an ordinary binary infix operator.

```
ΣM.A := M.C + M.E + r.A † F.A + r.B † F.B + r.D † F.D + r.G † F.G + r.H † F.H
e.n(t) := e.z † e.t(t)
```

Moment sums as r × F, and a unit normal as e_z × e_t. **3-vectors with a cross product are a
value-tower requirement**, alongside the complex arithmetic §8.2 finding 6 already established.

**6. Nested `≡` is equation construction, not only a boolean test.** Of 227 uses, 66 are root-level
global definitions and 161 are nested — but 133 of those sit directly inside `sys`, `at`, `FindRoot`,
`roots`, `solve` or `Solve`. The wiki corpus inverts that ratio rather than lacking the construct:
re-measured, its 81 nested uses are 24 in `if`, 35 chained inside another `≡`, 9 in `&`, 2 in `|`,
and only 7 in `solve`. §8.9 finding 6 read the dominant case correctly; it is just not the dominant
case here. Both readings are real and must be dispatched on context.

**7. The blocker is not the format. It is that two thirds of these are CAS worksheets.** 1.x
declares its plugins up front, which is the most useful thing the new container adds:

| Plugin | Files |
|---|---|
| X-Y Plot Region (JXCharts) | 45 |
| **MaximaPlugin** | 30 |
| CustomFunctions | 24 |
| Nonlinear Solvers | 11 |
| Mathcad Toolbox | 5 |
| DotNumerics | 2 |

Classified by what each worksheet actually needs: **40 files need computer algebra**, 13 need only
plugin numerics, 7 need only the `xyplot` region. **None of the 60 is dependency-free.**

The symbolic idiom is consistent: `Clear(t, φ, ω, N)` to make variables symbolic, equations built
with `≡`, then `Solve(sys(...), sys(unknowns...))` and `Assign(Sln)` to bind the result — plus
`at(diff(x(t),t), t ≡ 0)` (differentiation and substitution on an *undefined* function),
`Maxima(ratexpand(...))`, `Maxima(assume(4·c·m − d² > 0))`, and `MaximaTakeover(int)`, a
document-level switch rerouting a built-in through Maxima. `10.3_V.sm` writes the Newton–Euler
equations of a mechanism and solves them symbolically for F, A and B as functions of t.

**Nomo's no-CAS decision (§2) makes these unimportable as working worksheets by any amount of
importer effort.** That is a decision to record, not a gap to close. The open choice is what an
import *does* with them: emit the document with unsupported markers on the symbolic regions —
consistent with item 23, and it still delivers the prose, the plots and whatever numeric regions the
sheet has — or accept that this class of user does not migrate. It belongs in §11 either way.

The 13 numerics-only files need seven functions between them: `FindRoot` (2 files), `rkfixed` (3),
`lspline` (2), and the CustomFunctions helpers `cases` (5), `ltlt` (5), `ltle` (4) — piecewise over
chained comparisons — and `description` (6). All are implementable in a numeric engine, and that is
the whole shopping list for this tier. The rest of the plugin surface — `cinterp`, `csort`,
`sys2mat`, `linterp`, `identity`, `lele`, `norme`, `strrep`, `ODE.2`, `eigens_by_jacobi`,
`dn_LinAlgEigenvalues/Eigenvectors` — appears **only in files that also need CAS**, so implementing
any of it buys nothing until finding 7's policy question is settled. That ordering is the practical
value of this classification.

**8. Plot regions are configured from math regions through a property-path side-channel.** 159
operands across 23 files (109 distinct) are names like `XYPlot'Traces#0'Name` or
`VPlot'Labels'XLabel`, assigned from ordinary math regions to set properties on a plugin region.
They read as plain identifiers, so nothing breaks — but the document model needs somewhere for them
to land. Two details: the apostrophe is a separator here and prime notation elsewhere (`φ'`, `φ''`,
`x''.S` — 26 operands, kept apart by position), and eight names escape a literal apostrophe as
`\0027\`, so identifier text is escaped and must be unescaped.

**What this adds to §8.7.** Items 12 and 19 are superseded by findings 2 and 3; item 24 is closed by
finding 5; item 25 is answered — yes, and structurally. Two items to add: read the namespace and the
`<worksheet>` root before anything else, and use `<dependencies>` as the front page of the coverage
report, since the file states what it needs before a single token is parsed. One policy question is
now live rather than hypothetical: the trilingual edition carries all three languages in the same
file, so §8.9's note on which language an import keeps needs an actual answer. And when quoting
coverage over this corpus, count ~31 worksheets, not 60 — the two editions are near-duplicates.

### 8.11 §8.9 re-checked against the corpus (2026-08-26)

§8.10 turned up enough attribution slips in its own first draft to be worth asking whether §8.9's
figures hold. They were re-measured independently against the same 54 files. **Most reproduce
exactly.** Two do not, and the corpus has three region types nobody has listed.

**Reproduces to the digit.** The era split (35 files with `<e>` directly under `<math>`, 19 with
`<input>`, and exactly those 19 carrying no direct-`<e>` math at all); 247 `=` operators in 32 files
and 306 `<result action="numeric">` in the other 19 — disjoint, hence finding 2's 553 answers across
51 of 54 files; 197 `<contract>` elements, one per contract-bearing region; `decimalPlaces` (194) and
`trailingZeros` (25) as `<math>` attributes; **3878 regions, of which 424 at depth 1 and 18 at depth
2 — finding 5's 442 exactly**; `≡` 223 at root and 81 nested, for 304; the rare glyphs at 6 `—`,
3 `|`, 2 `†`; 199 distinct function names; and §8.6's 2162 math, 1540 text, 99 pictures, 49 plots.

**Wrong 1: the note about duplicated prose does not reproduce under any reading.** §8.9 closes with
"97 text regions carry the same prose twice under different `lang` attributes". Measured: of 1540
text regions, `lang` is `eng` on 1388, `ita` on 107, `rus` on 17, and absent on 28 — and the
non-English regions sit in **four files** (`PolyProperties`, `SimplySupportedTimberBeam`,
`Batchreactor`, `simpsonrichardson`). No text region carries more than one `<content>`; no two text
regions share a position with differing `lang`; only 4 prose bodies repeat under a different `lang`.
Nothing yields 97. **The language-policy question is real, but this corpus is not its evidence** —
§8.10's trilingual edition is, and that is where the decision should be argued from.

**Wrong 2: finding 8's numbers are right and its explanation is not.** 199 distinct names and 817
`el` are both confirmed. But the claim that the earlier 176 "counted the input side only", and that
`el` appears "817 times in all, but 454 times in expressions a worksheet asks to be evaluated",
describes a distinction that is not there: **exactly one distinct function name appears inside any
`<result>` in the whole corpus**, so input-side and total are the same measurement. The real split is
the era split again — 452 `el` under `<math>` directly and 365 under `<input>`; 76 distinct names in
the old shape and 151 in the new, union 199. §8.4's 176 was therefore an undercount from scanning one
era's shape, the same root cause as finding 1, and its "el (454 uses)" does not reproduce either —
the old-era count is 452. **No conclusion drawn from those figures changes**; `el` is still the most
common function by a wide margin. Only the reason for the gap does.

**Missing: three region payloads.** Alongside math, text, plot, picture and `area` (106), the corpus
contains **`writer` (9), `comboboxlist` (4) and `cflabel` (6)** — none named in §8.1, §8.9 or §8.7
item 4. The dispatch list was incomplete for the *old* corpus as well as the new one, which makes
item 4's rule — an unrecognised payload is a report, never a silent skip — the thing that actually
matters, rather than the list it enumerates. Old-era `<math>` also carries `evaluate` (1301),
`fraction-type` (461), `optimize` (445) and `error` (1) beyond the two attributes finding 4 names.

**`|` confirmed; `—` has a better hypothesis than "unknown".** All 3 uses of `|` sit in an `if`
condition between two comparisons, as §8.9 says. For `—`, the six uses are more specific than
recorded: **every one has a *function call* on its left — never a bare name — and a fully expanded
expression on its right**, e.g. `y(x) — (1000·(274250 − 108200·x) + …)/50000000` in `Newtoninterp.sm`
and `Jacobi(x) — mat(…)` in `NewtonRaphsonApplications.sm`. That is the shape of a **symbolic
evaluation display — the symbolic analogue of `=`** — and not a binding: the right side is the
expanded form of the left, which is what a stored result looks like, not what an assignment looks
like. If that is right, those six right-hand sides are stored symbolic answers and belong in the
oracle rather than in the binding logic. Still not implemented on a guess; still reported.

### 8.12 CAS: the measured case, and the plan that follows (2026-08-26)

§8.10 finding 7 reported that 40 of 60 mechanics worksheets need computer algebra and left the policy
open. Measuring it properly changes the shape of the problem, and the target user — **the practising
engineer doing dimensioned calculations, not the student following a symbolic derivation** — is now
settled, which closes it.

**1. The two corpora disagree by a factor of thirty.** Re-measured for CAS use: of the wiki corpus's
54 files by many authors, **exactly one** touches anything CAS-like (a single `simp` in
`simpsonrichardson.sm`), and no Maxima plugin appears anywhere in it. Two per cent there against two
thirds here. That is not two samples of one population. Kraska is the SMath community's principal
plugin author and the Maxima plugin's maintainer, and the book demonstrates the full stack; the
corpus measures expert capability, not field usage. **For the settled target user, the wiki corpus is
the representative sample and the mechanics corpus is a syntax and coverage source, not a
requirements source.**

**2. The 40 shrinks twice under inspection.** 30 files *declare* `MaximaPlugin` but only **20 call a
Maxima function**, and 8 of those 20 call nothing but `MaximaTakeover` — a scope switch, several of
them `MaximaTakeover(none)`, which turns it off. Declaring an assembly records what was loaded in the
session, not what the sheet needs. The genuinely Maxima-dependent set is about a dozen files.

**3. What the worksheets do symbolically is solve linear systems.** Of the 22
`Solve(sys(equations), sys(unknowns))` calls, **16 are linear in their unknowns** outright; the other
6 are single-equation solves such as `Solve(σ(y.N, z.N) ≡ 0, z.N)`, linear once the user's own
function is inlined. That is what statics is — ΣF = 0 and ΣM = 0 solved for reactions, with symbolic
coefficients like `b + c` and `cos α` in the matrix. Gaussian elimination over an expression field,
not integration or factoring. Meanwhile the functions that *look* symbolic are not: `solve` appears
44 times and is **always 4-argument** (SMath core's numeric root finder), and `int` 60 times, always
4-argument numeric definite integration.

**4. The decisive number is per region, not per file.** Of 2738 math regions, **211 — 7.7% — touch a
CAS function**, and the worst-affected file is 28% CAS. **786 of the 877 numeric stored results
(89.6%) sit in regions that do not.** A no-CAS Nomo importing this corpus therefore delivers roughly
nine tenths of every sheet's mathematics and can check itself against 786 stored answers *from the
corpus that supposedly cannot be imported* — plus the wiki corpus's 553.

**Decision.** *(The parked candidate below is re-costed in §8.40, which withdraws "bounded and
well understood": it holds only over an exact coefficient field, and these coefficients are
`f64`.)* No CAS, as §2 settled. The 211 CAS regions become visible unsupported markers per item
23; the 164 `<result action="symbolic">` values are recorded as provenance, never as assertions. The
one capability worth keeping on the shelf — **exact linear solve over symbolic coefficients**, plus
substitution and enough normalisation to display a result — is parked as a candidate, not scheduled.
It is bounded and well understood, it is what two thirds of these worksheets actually exercise, and
it does not drag in a CAS's open-ended surface. Revisit only on evidence from the target user's own
files.

#### The plan

Ordered so each phase is verifiable against stored answers before the next begins.

**Phase 1 — the reader, both eras.** Namespace-aware; dispatch on `<worksheet>` and `<regions>`
roots. Detect the era from structure (does a `<math>` contain an `<input>`?), never the version
string. Regions depth-first, pre-order. Payload dispatch must include everything both corpora
actually contain — math, text, plot, picture, area, **`xyplot`, `mathcadblock`, `image`, `writer`,
`comboboxlist`, `cflabel`** — and an unrecognised payload is a report, never a skip (§8.11).
Identifier text is escaped (`\0027\`); per-region `decimalPlaces`, `trailingZeros` and
`significantDigitsMode` override the document's `precision`.

**Phase 2 — semantics, where the silent bugs live.** Three rules, each measured:

- **`≡` dispatches on the shape of its left side, not its position.** Across both corpora, 289
  root-level uses split into 136 with a name (global definition, position-independent), 67 with a
  call `f(args)` (function definition), and **86 with an expression — a stated equation, not a
  binding**. Nested uses are equation construction or a boolean test by context (§8.10 finding 6).
  Item 10's "collect every `≡` in a pre-pass" would invent 86 bindings.
- **Assignment has four target forms:** a name (2544), `f(args)` (469), **`el(A, i, j)` — indexed
  assignment (103)**, and **`mat(...)` — destructuring a vector of names (31)**.
- **Units resolve; they are not read off `style="unit"`** (§8.10 finding 2). In-document declaration
  is day-one scope, in both the alias form (`VA : W`) and the magnitude form (`a.0 := 1·m`).

Value tower for this phase: binary64 real, complex (§8.2), **3-vectors with cross product `†`**
(§8.10 finding 5), matrices, strings, booleans — with units carried on the value.

**Phase 3 — the function surface, ranked by both corpora.** 97 distinct built-in and plugin names
are called across 114 files, over 4375 call sites once user-defined functions and CAS are excluded.
The distribution is steep and gives a real target:

| Names implemented | Call sites covered |
|---|---|
| top 10 — `el` `mat` `line` `eval` `sin` `sqrt` `cos` `if` `range` `for` | 69.5% |
| top 20 — + `description` `sum` `sys` `diff` `int` `augment` `abs` `solve` `transpose` `rows` | 84.7% |
| top 30 — + `stack` `vectorize` `length` `atan` `col` `num2str` `roots` `max` `FindRoot` `norme` | 91.5% |
| top 40 | 94.9% |

Take the top 30 as the v1 target and let the coverage report rank the tail; 25 of the 97 appear in a
single file and can wait indefinitely. Two notes on reading this list. `solve`, `int` and `diff`
belong in it as **numeric** functions — they are not the CAS surface. And it is not a list of core
built-ins: `description`, `FindRoot` and `norme` are plugin functions that rank this high, so the
plugin surface cannot be deferred wholesale to Phase 4.

**Phase 4 — plugin numerics, in payoff order.** The 13 mechanics files that need no CAS need seven
functions between them: `FindRoot`, `rkfixed`, `lspline`, `cases`, `ltlt`, `ltle`, `description`.
Everything else in the plugin surface — `cinterp`, `csort`, `sys2mat`, `linterp`, `identity`, `lele`,
`norme`, `strrep`, `ODE.2`, `eigens_by_jacobi`, `dn_LinAlg*` — appears **only in files that also need
CAS**, so it buys nothing until the parked decision changes. That ordering is the practical value of
the classification.

**Phase 5 — regions and document fidelity.** `xyplot` is declarative and easy; it also needs the
property-path side-channel (`XYPlot'Traces#0'Name`, 159 operands) to land somewhere in the document
model. `area` nesting, `picture`, `plot`, `mathcadblock`. Text keeps one language by an explicit
policy — the mechanics corpus is trilingual in one file (§8.10).

**Phase 6 — validation, built in from the start, not bolted on.** `<dependencies>` is the coverage
report's front page: the file states what it needs before a token is parsed. The oracle is **1339
numeric stored answers** — 553 from the wiki corpus, 786 from the CAS-free regions of the mechanics
corpus — compared after rounding to the *region's* precision and reading its `<contract>` unit.

**What is explicitly out of scope**, and emits a marker rather than an error: `Maxima`, `assume`,
`ratexpand`, `float`, `simp`, `Jacob`, `MaximaTakeover`/`Control`/`Define`; `Solve`, `Assign`,
`Unknowns`, `Clear`, `at`; symbolic `diff`/`int` over undefined functions; and the 164 symbolic
stored results.

### 8.13 Phase 1 built, and what building it corrected (2026-08-26)

§8.12's Phase 1 is implemented in the `nomo-smath` crate. Before it, the reader found
**0 of 60** mechanics worksheets — "no `<regions>` element", exactly as predicted. After it, all 60
read, and every count the reader produces matches the independent measurements in §8.10 to the digit:
2744 math regions (2738 plus the 6 `mathcadblock`), 93 `xyplot`, 125 pictures, 877 numeric stored
answers across 60 of 60 files, 477 with a `<contract>`, 14 regions already failing inside SMath. The
54-file wiki corpus is unchanged — 553 answers across 51 of 54, 197 contracts — so nothing regressed.

Four things were wrong in §8.10, and only writing the reader found them.

**1. 1.x nesting is not `<area>` containment — it is `<text>` containing `<regions>`.** §8.9 finding
5 established that from 0.88 an `<area>` *contains* the regions it collapses. That is true for
0.88–0.98 and **false for 1.x**, where `<area>` reverts to a bare marker
(`<area single="true" collapsed="true"/>`, 50 of them, none holding a region) and nesting moves
somewhere else entirely: a `<text>` region may carry `<regions type="content">` blocks of **inline
math set inside the prose**. Of the mechanics corpus's 308 nested regions, **174 arrive that way and
134 sit one level deeper inside those**. A reader that knows only the 0.88 rule finds none of them —
the third total-silence failure this format has produced, after the `<input>` shape and the
namespace. Both nesting sites must be read, and a `<text>`'s own prose must be scoped so it does not
swallow the text of the regions embedded in it.

**2. Inline regions are positioned relative to their text, and are not in position order.** Embedded
math sits at `top="0"`, `left="2"`, and a region's children are the concatenation of several
`<regions>` blocks — one per formula — so comparing positions across them reports an anomaly in a
quarter of the corpus that says nothing about the file. **Page-level order still holds in every file
of both corpora**, which is the property item 3 actually relies on. The order check is page-level
only, and deliberately so.

**3. Both editions are trilingual.** §8.10 called `Auflage 1` German-only. It is not: 413 of its
regions carry three `<text>` children. The split is emphasis — `Auflage 1` runs ger 536 / eng 428 /
rus 414, the other folder an even 490 / 489 / 489. So the language-policy question is not confined to
one folder, and 902 text regions across the corpus carry the same prose in more than one language.

**4. There are three result actions, not two, and only one is an assertion.** Besides 877 `numeric`
and 164 `symbolic` there are **10 `action="none"`**, and they are unevaluated equations — `k1 ≡
0.03·m`, `N ≡ G.1·cos α` — not numbers. Neither `symbolic` nor `none` may reach the oracle: **174
results are provenance**, kept for whoever reviews the migration, and 877 are assertions. §8.12's
1339-answer figure stands, because it already counted only the CAS-free numeric ones.

**Where Phase 1 leaves the import.** Of the 877 stored answers, 270 currently reach the checker in 39
worksheets; 58 can be compared and **52 agree (89.7%)**. The rest are blocked behind Phase 2 and 3
rather than behind the reader — 198 lines do not evaluate because a construct they depend on has not
been translated yet. The gap report now ranks that work directly:

```
   86  function   description      45  function   at          20  function   FindRoot
   54  function   Clear            40  function   vectorize   20  function   norme
   48  operator   †                26  function   Assign      16  function   ltle
```

`†` is the largest single non-CAS gap and the whole of Phase 2's vector work; `description`,
`vectorize`, `FindRoot`, `norme`, `ltle`/`ltlt`/`cases` are Phase 3 and 4. `Clear`, `at`, `Assign`,
`Solve`, `Unknowns` and the `Maxima*` family are the out-of-scope set from §8.12 and should stay in
this report as markers rather than being implemented.

### 8.14 Phase 2 built (2026-08-26)

§8.12's Phase 2 — the three semantic rules and the value-tower additions — is implemented. All 12
test suites green, clippy and `fmt` clean, the 11 golden snapshots byte-identical between native and
WebAssembly, and the no-host-math guard still passes.

**The cross product is in the engine.** `cross(a, b)`, three-dimensional only, dimensions falling out
of the products it is made of rather than from a rule of its own — `cross(r, F)` of metres and
newtons gives newton-metres. Requiring exactly three components is a real check rather than a
limitation: a seven-dimensional cross product exists in mathematics and in no worksheet, and the
restriction catches vectors that were meant to be dotted instead of silently returning a number. On
the importer side `†` now emits `cross(…)`, closing the largest non-CAS gap in the ranking (48 uses).

One display point worth recording: **`cross(r, F)` renders in joules unless asked otherwise**, since
J and N·m are the same dimension. Nomo's conversion syntax settles it — `M = cross(r, F) -> N*m` —
and that is also what an imported `<contract>` becomes, so the fix arrives with the importer rather
than needing a rule about moments.

**`≡` now dispatches on the shape of its left side.** A name is a global definition, a call is a
function definition, and **an expression is a stated equation that binds nothing** — Bernoulli
written out for the reader. Nomo has no statement asserting a relation without binding, so those
become comments carrying the equation verbatim: the worksheet keeps saying what it said and nothing
pretends to compute. This removed the "binding whose target is an expression" class from the report
entirely.

**Units resolve, in a pass of their own.** The new `resolve` module rewrites every unit-styled
operand that is not a unit into an ordinary name. A styled symbol is a unit only if the engine knows
it or **this document declares it**, and a declaration is a root-level positional binding whose value
is *unit-like* — literals, units, and the operators combining them. That last qualification matters:
`n : rows(X)` also has a unit-styled target, but a symbol bound to a computed value is a variable
however it is drawn, and declaring it a unit would put a matrix row count into the unit namespace.
The pass runs inside `read()` rather than in one consumer, because a worksheet that took
`style="unit"` literally is wrong for the coverage report, the emitter and the oracle alike.

Both declaration forms now emit: `VA : W` becomes `unit VA = W`, and `a.0 : 1 m` becomes
`unit a_0 = 1 m`. **The alias form had never worked** — the emitter matched a `Name` target where the
reader produces a `Unit`, so §8.7 item 13's day-one requirement was quietly unmet until resolution
gave the arm something to match.

**Two of the four assignment target forms have no Nomo equivalent, and that is a language question.**
A name and `f(args)` emit as before. `mat(a, b, …, rows, cols) : v` — 31 uses, how a solver result is
unpacked — now emits a temporary and one indexed binding per name, which says the same thing with
nothing added and stays a set of definitions. **`el(A, i, j) : x` cannot be translated at all**: it
mutates an existing value, and a worksheet is a set of definitions, not a script. 103 uses across the
corpora get a marker naming what they are. Whether Nomo should gain a form for either is a decision
for the language, not something an importer may invent.

**Effect, measured.** The wiki corpus moves from 215 of 242 comparable answers agreeing to **216 of
243** — the unit-declaration fix — and nothing regressed. The mechanics corpus stays at **52 of 58
(89.7%)**: its remaining answers are blocked on Phase 3 and 4 functions rather than on semantics, and
the report now says so precisely instead of misattributing them. The vaguest line in the report, "89
a definition of `…` with a computed parameter", fell to 8 and was replaced by 64 indexed assignments
and 25 unpackings — and all 25 of those fail on the *function* in the value, not on the unpacking,
which is exactly the Phase 3 work list pointing at itself.

### 8.15 Phase 3 built (2026-08-26)

§8.12's Phase 3 — the function surface — is implemented as far as it can honestly go. All suites
green, clippy and `fmt` clean, 11 golden snapshots byte-identical native and WebAssembly.

**Seven functions added to the engine**, all matrix or scalar plumbing with unambiguous semantics:
`rows`, `cols`, `row`, `col`, `augment`, `stack`, `sign`. A vector answers as the column it is —
`rows([1,2,3])` is 3 and `cols` is 1 — which is what indexing it already assumes. Joining refuses a
shape mismatch rather than padding: a table with a short column is a mistake, not a shape to repair.
`sign` is dimensionless by construction, and NaN stays NaN rather than being called positive.

**`vectorize` is dropped, not translated.** SMath's overbar forces an expression to evaluate element
by element instead of as matrix algebra — and Nomo's `*`, `^` and every scalar function are already
element-wise over a vector, verified directly (`sqrt([1,4,9] m²)` is `[1,2,3] m`). So the wrapper has
nothing left to say. It is dropped with a **note recording that a semantic marker was removed**,
because "it happened to mean the same thing here" is a claim a reviewer should be able to check.

**88 `description` calls were never a missing function.** Every one sits inside a `line(…)` block
that assigns to plot property paths — `VPlot'Labels'XLabel : description(text.phi)` — the
side-channel of §8.7 item 31. Reporting them as an unknown call to `description` put the corpus's
single largest gap under a name that explains nothing. A block whose statements *all* assign to
property paths is now recognised and reported as plot configuration for a named plot; a block that
also computes something is left alone, since dropping arithmetic because a plot was mentioned would
lose work.

**The gap report now attributes every plugin name.** From 1.x a worksheet declares its plugins in
`<dependencies>`, so this is not guesswork — the file says. "We have never heard of this name" and
"this is Maxima, which Nomo does not have and will not get" are different answers, and only the
second is a decision rather than a gap. `†` is out of the unidentified list, `|` and `—` remain.

#### What was left undone, and why

Three names in the ranking are **not** implemented, and the reason is the same in each case: the
corpus does not settle their meaning, and this note's standing policy is not to implement on a guess
(the `range`-with-a-step precedent).

- **`ltle`, `ltlt`, `lele`** (27 uses) — chained comparisons in the `cases` piecewise. The naming
  scheme is almost certainly `[first][second]`, so `ltle` is `a < x ≤ b`, and the *existence* of a
  separate `lele` is real evidence for that reading, since it would otherwise be redundant. But
  "almost certainly" decides which endpoint of a beam belongs to which segment, and nothing in the
  corpus's stored answers pins it. `cases` waits on them.
- **`norme`** (20 uses) — presumably a Euclidean norm, which `sqrt(dot(v, v))` would give. One use
  is `σ.1 : norme(n)` with a stored `58.3 MPa`, so the oracle *could* settle it; it has not been
  checked yet, and until it is the name stays reported.
- **`F`, `A`, `B`, `P`, `Q`, `M`** (51 uses) — called but never defined in their own document. They
  are bound by `Assign(Sln)` from a symbolic solve, so they are CAS-dependent rather than missing.

`diff`, `int`, `solve`, `roots` and `FindRoot` are genuinely numeric and genuinely wanted, but they
are numerical methods rather than function-surface plumbing, and they belong to Phase 4.

#### Effect, and one thing that got worse

The emitter's two largest untranslated classes fell from 488 and 445 to **455 and 405**, and the
vaguest entry in the ranking became 24 honestly-labelled plot-configuration blocks.

**Agreement did not move: 216 of 244 in the wiki corpus, 52 of 58 in the mechanics corpus.** More
lines now evaluate, and some of them evaluate on values that an *earlier* failure had already left
incomplete. `ImplicitFunctionGrapher.sm` is the clean example: `rows(Points)` now computes, and
answers 2 against SMath's 1188, because the loop that fills `Points` uses an indexed assignment Nomo
cannot express, so `Points` is still the placeholder it was initialised as. That is one more
disagreement and one fewer worksheet checking out completely.

This is worth stating plainly rather than smoothing over: **adding functions moves failures from
"did not evaluate" to "evaluated and disagreed", and the second looks worse while being more
informative.** The report already separates them — all 28 wiki disagreements and all 6 mechanics ones
are in worksheets that did not translate completely — so nothing here is an engine error. But the
headline percentage is not a progress metric while translation is incomplete, and it should not be
read as one.

### 8.16 Phase 4 built (2026-08-26)

§8.12's Phase 4 — plugin numerics in payoff order. All suites green, clippy and `fmt` clean, 12
golden snapshots byte-identical native and WebAssembly, no-host-math guard passing.

**Three functions added to the engine**, all reached through the existing higher-order mechanism —
`map` and `iterate` already take the *name* of a function, so `root` and `integral` do too, and no
lambda had to be invented for them.

- **`root(f, a, b)`** — a root by bisection. Bisection rather than Newton for the reason `iterate`
  takes a count rather than a tolerance: no derivative, cannot diverge, the same number of steps on
  every machine, every step a comparison and a midpoint. 100 halvings exhausts a binary64 interval
  whatever its exponent, so "until there is nothing left to halve" is written as a count that
  provably terminates. **It requires a bracket** and refuses without one — a confident wrong root in
  a structural calculation is the worst outcome available.
- **`integral(f, a, b)`** — Simpson's rule over a fixed 1024 panels. Fixed rather than adaptive
  because an adaptive scheme's subdivision depends on comparisons against a tolerance, so two builds
  disagreeing in the last bit would then disagree in how many panels they used and by far more than a
  bit. Exact up to a cubic, which covers the load shapes a beam calculation uses. Nodes are computed
  as `a + i·h`, never by repeated addition — `range`'s rule, for `range`'s reason.
- **`norm(v)`** — the Euclidean norm, dimension surviving because the squares and the root cancel in
  the dimension exactly as in the number.

**`int(expr, x, a, b)` is lifted, not renamed.** SMath passes an expression and the name of its free
variable; Nomo has no lambdas by design. The integrand is therefore emitted as a named definition
above the line that uses it and the call refers to it — a real translation, and the reason the
emitter now buffers a line rather than writing it as it goes.

#### `norme` settled by arithmetic, and it was worth the trouble

§8.15 left `norme` unimplemented pending evidence. The evidence was in the corpus. `7.3.sm` runs a
power iteration, and after each `σ.1 : norme(n)` it computes `n.0 : n/σ.1` — whose stored answers are
`(0.857, 0.514)`, `(0.967, 0.256)`, `(0.938, 0.348)` and six more, every one of them a **unit
vector** to the precision stored. Only the Euclidean norm does that. This is the oracle doing exactly
what §8.7 item 22 exists for: settling a third-party plugin's semantics from the worksheet's own
recorded answers rather than from its name.

It was also the single largest win in four phases. **The mechanics corpus went from 52 of 58
comparable answers agreeing to 68 of 74 — 91.9%** — because the whole eigenvector iteration unblocked
at once.

#### `solve` deliberately not translated, and the corpus is why

Nomo's `root` takes exactly the shape of SMath's `solve(expr, x, a, b)`, and mapping one to the
other is the obvious move. **The corpus disproves it.** With the mapping in place, four regions hand
`solve` a range across which the expression does not change sign — and SMath still answers. Its two
limits are therefore a *search range*, not a bracket, and the two functions are different algorithms
wearing the same shape.

Where the range happens to bracket, they agreed exactly: the mapping bought five agreements in the
wiki corpus. It is still wrong to keep. A root finder that is right most of the time is worse than
one that says it cannot tell, and mapping a name onto a different algorithm is precisely what §8.7
item 8 and the `range`-with-a-step precedent forbid. 44 uses stay reported with that reason attached.
`root` remains in the language on its own merits, and is ready if `solve`'s semantics are ever pinned
down.

#### Where the four phases leave the import

| | wiki corpus | mechanics corpus |
|---|---|---|
| Worksheets read | 54 of 54 | **60 of 60** (was 0) |
| Answers compared | 245 of 402 | 74 of 280 |
| **Agreement** | **217 of 245 (88.6%)** | **68 of 74 (91.9%)** |

Both agreement figures are limited by translation, not by arithmetic: every one of the 34
disagreements across both corpora is in a worksheet that did not translate completely, where a
dropped construct leaves a stale value that still evaluates. The mechanics corpus's low
comparison rate is §8.12's 7.7% CAS share plus the constructs listed in §8.15 as deliberately
unimplemented, not engine gaps.

### 8.17 Phase 5 built (2026-08-26)

§8.12's Phase 5 — regions and document fidelity. All suites green, clippy and `fmt` clean, 12 golden
snapshots byte-identical native and WebAssembly. Agreement is unchanged in both corpora, which is the
point: this phase is about what an import *keeps*, not what it computes.

**Three things the reader was dropping silently.**

1. **`<math><description>` — 221 of them.** Not decoration: the `description(x)` function *reads*
   this text, so a worksheet that labels a plot axis keeps the label here and nowhere else. Before
   this, `Schwinger.sm` imported `xlabel = 1` with the string "Time in s" nowhere in the output —
   a binding to a number whose entire meaning lived in an element the reader never opened. Now the
   note is emitted above the line it annotates.
2. **The prose of every language but the first.** The reader kept a list of *language codes* and the
   text of only the first region, so no downstream policy could have chosen differently even if it
   wanted to. It now keeps `(language, prose)` for every variant.
3. **Escaped characters in names.** `\XXXX\` escapes a character by code point:
   `\007B\labels\007D\\0027\XLabel` is `{labels}'XLabel`. 392 across both corpora, all of them `{`,
   `}` or `'`. A name left escaped is a different name, so this is undone once in the reader rather
   than at each place a name is compared (§8.7 item 30).

**The language choice is now an argument, which is what makes it a policy.** `emit_in(w, lang)` and
`smath-import --lang eng`; a region without the requested language keeps its first rather than losing
its prose, and what was dropped is reported once at the end rather than at each of the 900-odd
regions it applies to. Running the mechanics corpus with `--lang eng` produces an English worksheet
from the same file that produces a German one by default — which is the check that this is a real
choice and not a relabelled first-match.

**Plots keep what they plotted.** `' [import] unsupported: a plot` threw away the expression along
with the chart. It now reads `a `xyplot` of x(t*s)/cm`. Making that work exposed a second gap: the
name table was built from math regions only, so a variable appearing solely in a plot had no Nomo
spelling and the plot reported as untranslatable for want of a name it shared with the lines above
it.

#### The page is two-dimensional and the file is not

The most visible defect in an imported worksheet is that labels read *after* the values they
describe. `Schwinger.sm` writes "Federsteifigkeit" at `left=0, top=180` and `c := 1 N/cm` at
`left=135, top=171`: side by side on the page, nine pixels apart vertically. File order — which §8.3
established is correct, and which is genuine page reading order — visits the value first.

**This is not a bug and it was tempting to treat it as one.** Re-associating prose with values needs
the layout, and the layout does not support it: of the mechanics corpus's 2744 math regions, only
**716 have exactly one candidate label to their left on the same row**, 107 have several, and 1915
have none. Re-pairing would be guesswork on a quarter of the document and wrong somewhere inside it,
and a comment attached to the wrong value is worse than one that reads a line late.

So the regions' boxes are now read and kept, the count is measured, and each import says once how
many values had prose beside them — 149 such notes across the mechanics corpus. The reader is told
the page was two-dimensional instead of being left to assume every comment introduces the line
beneath it. If the association is ever attempted, the numbers above are what it has to beat.

### 8.18 Phase 6 built, and a caveat on every figure above (2026-08-26)

§8.12's Phase 6 — validation, built in rather than bolted on. All suites green, clippy and `fmt`
clean, 12 golden snapshots byte-identical native and WebAssembly.

**The manifest is the coverage report's front page.** `<dependencies>` is now read, and the report
opens with what the worksheets say they need before a token is parsed — 45 X-Y Plot, 30 MaximaPlugin
(marked out of scope), 24 CustomFunctions, 11 Nonlinear Solvers, 5 Mathcad Toolbox, 2 DotNumerics.
Exactly the §8.10 figures, now produced by the tool rather than by a script.

**The corpora are a regression gate, not a report.** `scripts/check-corpus.sh` compares a committed
per-worksheet baseline in `tests/corpus/` and fails on any difference; `--write` accepts an intended
change so it lands in the diff beside the code that caused it. This is the §9 discipline, taken from
CalcpadCE, applied to the importer. `smath-import --check` alone still exits zero however bad its
numbers are — every one of them is work to do, not a regression, and a tool that failed the build for
measuring honestly would stop being run. The baseline is the opposite: it says nothing about how good
the import is and everything about whether it changed.

The corpora are third-party worksheets held outside the repository, so this runs locally rather than
in CI. That is a real limitation and worth stating rather than papering over.

**§8.7 item 22 needs correcting.** It says to round a stored answer to the region's precision before
comparing. The oracle deliberately does *not* consult the setting, and it is right not to: a stored
literal states its own precision, `1.8491` means ±0.00005 of a mantissa, and scaling by
`expected / 1.8491` carries that through the exponent and the units at once. Reading `precision` as
decimals of the value makes the tolerance a hundred thousand times too tight on any answer SMath
wrote in scientific form. The per-region `decimalPlaces` and `significantDigitsMode` found in §8.10
are worth *reading* — they are part of the document — but the comparison must not use them.

#### The caveat, which is the most important thing in this section

Testing the gate by deliberately breaking `norm` — returning the sum of squares instead of its root —
**changed nothing in the mechanics corpus**. Same 68 agreements, same 74 comparable, every
per-worksheet count identical. A gate built on verdict counts would have passed a plainly broken
engine.

The reason is worth recording. Sixteen of that corpus's agreements come from `7.3.sm`'s power
iteration, and what they compare is `atan(n[2]/n[1])` — **an angle, which does not change when the
vector it came from is scaled**. Break the norm by any factor and the eigenvector still points the
same way. Those sixteen answers validate that the worksheet *translated*; they do not validate the
arithmetic underneath.

Two consequences.

1. **The baseline carries a digest of every computed value**, not just the verdict counts. With it,
   the same break is caught immediately and names the two worksheets whose values moved while their
   counts stood still. Determinism is what makes this possible: the engine is required to give the
   same bits everywhere, so a digest is a legitimate gate rather than a flaky one.
2. **The agreement figures in §8.14–§8.17 measure translation at least as much as arithmetic**, and
   should be read that way. "68 of 74 agree" means 74 answers were reachable and 68 matched — not
   that 68 independent numerical results were confirmed. §8.15 already warned that the percentage is
   not a progress metric while translation is incomplete; this is the sharper version of the same
   point, and it was found by attacking the gate rather than by trusting it.

### 8.19 Figures carried and shown (2026-08-27)

§8.12's Phase 5 listed `picture` among the region payloads still to do. It is done, and the file that
forced it is the interlock worksheet: 908 KB, of which **864 KB is base64** — 20 PNGs totalling 633 KB
around **77 lines** of mathematics. For that document the figures *are* the document, and an importer
that emitted 20 markers had not migrated it. The corpora hold 224 pictures between them, so it was
never one file's problem.

**The data goes in a trailer, not where the figure stands.** A `.nomo` file is its own source text
(§7), so an image can only live in it as base64, and the largest here is a 116 KB line. Put in the
body it destroys the property the text format was chosen for. Collected at the end, the body reads
as it always did — 77 lines, none over 80 columns — and the blobs are one contiguous, append-only
region a `.gitattributes` rule can mark `-diff`.

**External files beside the worksheet were the alternative, and the browser settles it.**
`web/src/storage.js` opens a *file* handle, not a directory; Firefox and Safari get `<input
type="file">` and no filesystem at all. Inline is the only form that survives every path the
application already supports, and it is what keeps `nomo html` the single self-contained document it
promises to be — each figure becomes a `data:` URI.

**Every line of the format is a comment**, which is what `' nomo 1` already is. A worksheet carrying
figures therefore opens in a build that has never heard of them, showing its trailer as the comments
it is rather than failing to parse — the "old worksheets must always open" constraint of §7 honoured
in advance instead of retrofitted. The cost is stated rather than hidden: an image is not a
statement, so nothing can compute one. That is the right trade while a figure is scanned evidence
rather than a result, and the reference line is what becomes a real statement if it ever stops being.

**Reading it decodes nothing.** The base64 is carried as text and handed to the `data:` URI
unchanged, so no host facility is involved and the determinism guard is untouched — confirmed by
`compare-targets.sh`, which finds the worksheet with the embedded PNG byte-identical native and under
WebAssembly. Untrusted payloads are refused rather than embedded: a `.nomo` may have been written
out of a third-party `.sm`, so anything that is not base64 under a media type we can *name* becomes a
visible note. Guessing a media type for an unknown format would produce a broken image where an
honest report belongs.

**A silent loss, found by checking the round trip rather than the counts.** The first import returned
19 of 20 images. That worksheet has **two** top-level `<regions>` blocks — `type="content"` and
`type="header"` — and the reader took the first, dropping three regions (one text, one picture, one
math) with no marker and no count. It is the only file of 117 with a second block, which is how a bug
like that survives being measured twice. The header is page furniture: an author, a company logo, and
the date `04-04-2025`, which SMath stores as *arithmetic* — three operands and two subtractions.
Emitted into the body that is a query evaluating to -2025, so header mathematics is **shown and not
run**, the treatment a plot's expression already gets, and its logo is carried like any other figure.
Nomo has no page model, and this invents none.

Across both corpora the change moved 82 worksheets' `unsupported` counts and **not one computed value
or answer verdict** — which is what a document-fidelity change should look like against §9's two
gates.

### 8.20 Free symbols refused, and counted (2026-08-27)

The interlock worksheet again, and this time the file was right and the importer was wrong. One
region reads

```text
Vout : (R851 + R850)*R840/((R840 + R841)*R850)*V2 - R851/R850*V1
```

and `V1` and `V2` occur **once each in the whole 908 KB file**, here, bound nowhere. Four lines
later the same `Vout` is reassigned with every resistor and voltage written out as a literal, and
that second one is what feeds the rest of the worksheet. The first is the generic transfer function
of the differential amplifier, written for a reader. The importer emitted it as Nomo source, so a
worksheet that had imported "cleanly" opened in the editor with two undefined names and nothing to
say why.

**SMath did not consider it an error, and the file proves it.** SMath persists a failed region: the
`error="N"` attribute of §8.10 finding 4, with `#` for a result. It carries **zero** of them.
What that region carries instead is `optimize="2"` — symbolic optimization, which hands the region to
SMath's CAS, where an unbound name is a free symbol rather than a failure. 351 regions across 48
corpus files are set that way. So this is not a broken worksheet; it is a construct the format
supports and Nomo, having no CAS (§8.12), does not.

**A name nothing binds is now a marker, not a line.** The rule is the intrinsic one rather than the
attribute: **Nomo has no free symbols**, so a statement mentioning a name the document never defines
cannot be written out as source whatever the region's optimization is set to. The marker names the
symbols, adds the region's own evidence where it has any — *"and SMath kept the region symbolic"* —
and the translated line survives underneath it as a comment, where it can be read but cannot be
mistaken for something the engine ran. Free is judged across the whole document, never up to the
point of use: a name defined *below* its use is a scope question, already reported as
`ScopeFlattened`, and conflating the two would file a working worksheet under the wrong complaint.

**What the corpus turned out to be hiding.** 268 regions across the 114 worksheets, and only one of
them is the interlock worksheet's. The rest are three kinds, all of which were emitting broken source
in silence:
unit labels typed as bare math regions beside a number (`ft`, `s`, `lb` — 21, 20 and 7 uses, an
older-era habit); the symbolic-solve idiom, where `A.x`, `A.y`, `S.1` are the *unknowns the worksheet
exists to solve for* and go to `Solve`/`Assign` from `CustomFunctions` — the same names §8.10 finding
2 met wearing `style="unit"`; and a free `i`, which in SMath is the imaginary unit. That last one
gets its own clause in the marker, because "a variable nobody defined" and "complex arithmetic Nomo
does not have yet" are different work for whoever reads the report, and `i` is also the commonest
loop index there is — so the marker says what SMath means by it without deciding which this is.

**The cascade is deliberately not followed.** A commented-out definition leaves its dependants
undefined, and those lines still emit. Marking them too would delete a whole dependency chain from
the worksheet to hide an error whose root cause is sitting three lines above it, already marked.

**Against §9's two gates:** the golden suite is untouched, and across both corpora **no worksheet
lost an agreed answer and none gained a disagreement**. The only oracle movement is `answers`
falling in 12 mechanics worksheets, all of them assertions that were `unevaluated` — Nomo could not
compute them before either, and a comment is not a result to check. `unsupported` rises 562 → 732 and
1126 → 1224, which is the number this change exists to produce: 268 gaps that were previously
invisible.

### 8.21 The plot span, settled by reading SMath (2026-08-27)

**The question.** A `<plot>` records `scale_*`, `rotate_*` and `transpose_*` and nothing else —
checked across all 89 plot regions in the three corpora, and true of SMath 1.5's own bundled
examples too. For a plot of a function of `x` the domain is exactly what SMath evaluates over, so
without it the importer could only refuse. Two earlier attempts to decode the viewport disagreed on
the pixels-per-unit constant by four orders of magnitude, and this note recorded the honest position:
settleable, but only with ground truth.

**What settled it.** SMath Studio 1.5 is installed on the development machine, so the ground truth
was available in a better form than a screenshot: `plugins/…/PlotRegion.dll`, disassembled. Three
facts, each read off the IL rather than inferred:

1. `Renderer`'s constructor sets `limits_x = limits_y = limits_z = 10`, and loading a plot resets
   the frame — for a **2D** plot (`type="2d"` reads as `PType == 0`) to `10·(w/h)/1.66`, where `w`
   and `h` are the canvas size. The `1.66` is a literal in that branch.
2. `Renderer::Scale(a, b, c)` multiplies **both** the saved `scale_*` and the live `limits_*` by the
   same factors, and the restore path calls `Transpose(stored)` then `Scale(stored)` exactly once
   per load. So a reloaded frame is `10·(w/h)/1.66·scale_y`.
3. The plotting method takes the visible horizontal extent as `±w/2` divided by that frame, then
   shifts both ends by `−transpose_x` divided by the same. One sample per pixel column.

So the domain is

```
    frame = 10·(w/h)/1.66·scale_y
    x ∈ [ (−w/2 − transpose_x)/frame , (+w/2 − transpose_x)/frame ]
```

**The field names are crossed**, and this is the trap that cost the earlier attempts: the
*horizontal* extent divides by `limits_y`, which is what `scale_y` scales. Reading `scale_x` gives
spans that are absurd in every worksheet — a standard normal over ±0.73.

**Checked against six worksheets, none of which records its domain anywhere.** The standard normal
comes out over ±4.80 and peaks at 0.398942 = 1/√(2π); Student's *t* over −4.10…3.87; χ² over
−1.97…25.9; F over −0.41…2.78; a Newton-Raphson demo over −4.93…7.39. And the converter worksheet's
three-curve
LLC gain plot comes out over **25.5 kHz…202.6 kHz** — which is the span `examples/plots.nomo`
already draws that worksheet's gain family over, chosen there by reading the worksheet and here by
arithmetic on its viewport. Six independent agreements, one of them numerically against a span this
repository had already committed to for other reasons.

**What is still approximate.** The width used is the region's stored box; SMath measures the canvas
inside it, and a region carries a few pixels of frame — the same few pixels that make an imported
`<picture>` about five pixels a side larger than SMath drew it (§8.19). The span is therefore right
to about a percent at the edges rather than to the last bit, and it is written to six figures to say
so. Pinning it exactly would need the canvas geometry, which is in `SMath.Controls`, not here.

**Also found while looking.** The plot region has explicit axis limits — `limits_x/y/z`,
`HasLimits`, `LeftLimit`/`RightLimit`/`TopLimit`/`BottomLimit` — and **no worksheet in any of the
three corpora, nor any of SMath's own examples, sets them**. When one does, the domain is in the
file and needs none of the above. And `sys(s1, …, sn, n, 1)` is confirmed from the same source as a
list of series carrying a shape in its last two operands, which is how the importer reads it.

### 8.22 A definition that is really a function of `x` (2026-08-28)

**What was blocking three charts.** §8.21 answered what span a `<plot>` was drawn over, and
the converter worksheet's charts still did not draw. The obstacle was one step further back and had
nothing to do
with plots: the worksheet writes

```text
plot_Z_LLC_eq : Z_LLC_eq_abs(x)
```

and then plots `plot_Z_LLC_eq/ohm`. SMath has **no function-valued definition** — there is nowhere
to write the parameter — so naming a curve before drawing it means writing an ordinary definition
whose right-hand side is free in the plot variable. SMath's CAS keeps the region symbolic (the
`optimize="2"` of §8.20) and the plot below evaluates the name at each sample. Read literally, the
line binds nothing: §8.20's rule correctly made it a marker, and then the plot correctly reported
that the name it draws has no value. Two right answers to the wrong question — the definition is not
a broken line, it is a function of `x` written the only way the format allows, and it is
`fn plot_Z_LLC_eq(x) = Z_LLC_eq_abs(x)`, which is exactly the shape Nomo's `plot` wants.

**Four conditions, all of them the worksheet's own evidence.** This is a reinterpretation of a
statement, so it is fenced by what the file says rather than by what worksheets usually mean:

1. The definition's body **reads `x`** — SMath's 2D plot variable, the same one the plot path
   already keys on, and the variable every function plot in all three corpora is written in.
2. A **plot region reads the name**. Without a plot there is nothing saying the definition was meant
   as a function, and inventing a parameter would hide an ordinary broken line. A definition free in
   `x` that nothing draws still gets §8.20's marker.
3. **Nothing else reads the name.** A name read as a value somewhere else is not a function, and
   turning it into one would break the line that reads it. This is a condition rather than an
   assumption because the corpus contains the case: `7.4.sm` in the mechanics corpus defines `P`
   twice as a `sys(…)` of parametric curves, and the second definition reads the first. It is the
   only candidate in 118 worksheets that this rejects, and rejecting it is right.
4. `x` is the **only thing the body is waiting for**: `x` has no value at that point in the page, and
   everything else the body reads does. `x : 5` above the definition means `sin(5)`, a number; a
   dependency that did not import means a broken line, which keeps the marker it already had.

The first three are decided in a pre-pass over the document; the fourth only emission knows, so it
is asked there. A name that clears all four is written as a function and *is* one from that point:
calls to it spell, and the plot that draws it applies it to `x` — `plot_Z_LLC_eq/ohm` is drawn as
`plot_Z_LLC_eq(x)/ohm`, which then takes the ordinary path for a function of `x` and is lifted into
a curve over the span §8.21 derives. A plot that draws nothing but the curve itself skips the lift
and names the worksheet's own function, so the chart line reads as what the author wrote. A
candidate whose definition did *not* import is never applied to `x`, so its marker keeps naming the
plain name the file holds.

**Effect.** Six definitions across four worksheets are functions now: `plot_Z_LLC_eq` and
`plot_Z_LLC_angle` in the converter worksheet, and the vertical marker lines `liner`, `lineL`,
`lineR` in the
three distribution worksheets — those last were emitting as live, broken definitions before, since
`x` is a parameter name elsewhere in those files and therefore not free by §8.20's document-wide
test. The converter worksheet goes from **16 import markers to 11**, and two of its three charts
draw, over
53.0–125.4 kHz and 62.2–132.6 kHz. Across the three corpora markers fall 1619 → 1614; every one of
that change is that worksheet, since the other three traded a broken line for a function
rather than a marker for a line.

**Against §9's two gates:** the golden suite is untouched, the corpus baselines are unchanged, and
the oracle does not move at all — 507 of 537 comparable answers agree before and after, and
it stays at 30 of 30. That is the expected shape: this makes lines *exist* that did not, and
none of them carries a stored answer, because a plot has no result to store.

**What is still left in the third chart.** `Multipleplots : sys(Mg(x), Mg2(x), 2, 1)` clears

### 8.23 `sys(…)`, and where a list of curves belongs (2026-08-28)

**The last thing between the converter worksheet and its third chart.** §8.22 made a definition free
in `x` into
the function it is, and one of the three plots still would not draw:

```text
Multipleplots : sys(Mg(x), Mg2(x), 2, 1)
```

`sys` is confirmed from `PlotRegion.dll` (§8.21) as a list of series carrying its shape in the last
two operands, and the importer already unpacked one written *inside* a `<plot>`. This one is written
on a definition, which is the same thing SMath's missing function-valued definition forces: there is
nowhere else to write "these two curves, together", so the author names them and plots the name.

**A list of series is a plot, not a value.** Nomo has no value for one and does not need one. The
definition writes nothing and records its series for the plot that reads it; the plot expands the
name and draws them. Nothing is dropped: it is a `Carried` note rather than a marker, because the

**Effect.** The converter worksheet draws all three of its charts and goes from 11 import markers to

### 8.24 SMath's `solve`, read rather than inferred (2026-08-28)

**The open question.** §8.16 refused to translate `solve(expr, x, a, b)` onto Nomo's `root`, and
gave the evidence: four corpus regions hand `solve` a range across which the expression does not
change sign and SMath still answers, so its two limits are a *search range* rather than a bracket.
That refusal was right and it left the question open — "44 uses stay reported until the semantics
are pinned down". They are pinned now, and not by inference.

**Where it lives, which took some finding.** `solve` is not in `SMath.Math.Numeric.dll`, and the
core assemblies are string-compressed by SmartAssembly, so grepping for the name finds nothing.
Following `SMath.Manager.Functions::get_Solve` — a property, and therefore a name that survives
obfuscation — leads to `plugins/…/SpecialFunctions.dll`, which is also the only assembly outside
`SMath.Manager` that reads `SessionProfile::SolveFromPoint` and `SolveToPoint`. Method names there
are obfuscated to `''` and the IL is not: constants, control flow and calls all read plainly, the
same way `PlotRegion.dll` did in §8.21.

**The algorithm, from the IL.** `solve(expr, x, from, to)`:

1. If the last term of the expression is `<`, `>`, `≤`, `≥` or `≠` — throw. If it is `≡`, clone the
   terms and **replace the equals with a minus**, so `solve(f ≡ g, …)` is `solve(f − g, …)`.
2. `step⁻¹ = 200/(to − from)`, and a loop counter `(to − from)·step⁻¹`, which is 200 up to rounding.
3. Walk `i` from 0: `x = Round(from + i/step⁻¹, 14)`, evaluate, and record the sign. An exact zero at
   a sample is a root and suppresses the next comparison. A sign change between neighbours starts a
   refinement.
4. The refinement is a **secant with one endpoint held fixed**: `x₁` is the sample where the sign
   changed, `x₀` starts one step below it, and `x₀ ← x₀ − (x₁ − x₀)·f(x₀)/(f(x₁) − f(x₀))` runs at
   most **100 times**, stopping when the estimate moves by less than `10^(−DecimalPlaces)`.
5. A root already in the list, or outside `[from, to]`, is dropped. **No roots at all throws**; one
   root returns a scalar; several return an `n`×1 matrix.

So it is a **scan**, exactly as §8.16 deduced from the outside, and the deduction can now be made
sharper: what the earlier analysis measured as "no sign change" was the sign at the two *ends*. The
200-point scan sees interior crossings that an endpoint bracket test cannot, which is the whole of
the difference between the two functions.

**Checked against the corpus before anything was built.** A 30-line simulation of the above,
against worksheets whose expressions are simple enough to transcribe:

| worksheet | call | SMath stored | simulation |
|---|---|---|---|
| `5.1.sm` | `solve(Q(x·m), x, −4, 4)` | `[−3.08, 1.08]` | `[−3.0817, 1.0817]` |
| `5.1.sm` | `solve(Q(x·m), x, 0, 2)` | `1.08` | `1.0817` |
| `NewtonRaphsonApplications.sm` | `solve(x² − 2x − 5 ≡ 0, x)` | `[−1.4495, 3.4495]` | `[−1.44949, 3.44949]` |

Including the **order**: roots come back in scan order, and the stored vectors are in that order.

**`diff` is a different answer: it is the CAS.** The same search finds no numeric differentiation
anywhere. `SpecialFunctions.dll` mentions `Diff` only in the region *painter* and in the branch that
sets `Optimization = Symbolic` before handing the expression to `SMath.Math.Symbolic`, where
`Expression` builds a `diff(a, b)` term for the algebra to reduce. SMath's derivative is symbolic,
and §8.12 already settled that a CAS is out of scope. This is therefore not an open question any
more but a closed one: `diff` cannot be translated, the reason is architectural rather than unknown,
and the marker should say so. That is what blocks the converter worksheet's last three answers,
since
`Min_fsw_calc` solves the zero of a symbolic derivative.

**What Nomo does with this: a new function, not a copied algorithm.** `roots(f, a, b)` — every root
in a window — is a primitive worth having on its own merits, and the shape SMath's `solve` has.
Three departures, all in the direction of an answer that depends on nothing but the arithmetic:

- **200 intervals, both ends included.** SMath's loop bound is `(to − from)·(200/(to − from))`,
  which is 200 or 200±1 ulp depending on the range — so whether SMath samples the far end at all
  depends on float rounding. Nomo samples `a + i·(b − a)/200` for `i = 0…200`, which is how `range`
  and `plot` already compute their nodes, and misses no root at the top of the window.
- **No `Round(x, 14)` on the sample points.** That is SMath papering over accumulated float drift in
  a sum it did not need to accumulate; computing the node directly has nothing to paper over.
- **Bisection instead of the secant.** The secant with a fixed endpoint can leave the bracket that
  found it; bisection cannot, it needs no tolerance at all — the midpoint coinciding with an
  endpoint *is* an exhausted interval — and it is already the method `root` uses and this note
  argues for. Both converge to the same root inside the same bracket, so the answers agree to well
  inside the precision SMath stored. Critically, SMath's stopping rule is `10^(−DecimalPlaces)`:
  **its answer depends on the worksheet's display precision**, which is exactly the kind of coupling
  this project exists to remove.

**A name collision, found the hard way.** SMath also has `roots(expr, x, guess)` — a *local* search
from a starting point. `5.1.sm` writes `roots(Q(x·m), x, −1)` for `1.08` and `roots(Q(x·m), x, −1.1)`
for `−3.08`: two guesses a tenth apart, two different roots, which is what a local method does and a
scan never does. The operands line up with Nomo's `roots(f, a, b)` — three of them, a name and two
numbers — so the moment `roots` entered `BUILTINS`, **26 corpus regions across 14 worksheets** began
translating silently and wrongly. Every gate stayed green: the answers those lines produce are
numbers, so nothing failed to evaluate — and it was the new **source digest** in the corpus
baseline, added two commits earlier, that made the change visible at all. The importer now refuses SMath's `roots` by name, and the lesson is recorded
here: a Nomo builtin gaining a name can change what an imported worksheet means, and name identity
is not evidence of meaning.

### 8.25 `solve` translated, `diff` closed (2026-08-28)

**What §8.24 pinned, this builds.** `solve(expr, x, a, b)` becomes `roots(zero_n, a, b)`, with the
expression lifted into a function the way an integrand already is, and `solve(f ≡ g, …)` lifted as
`f − g` — the same rewrite SMath performs on the term list before it searches. `solve(expr, x)` with
no range is refused, and the reason is worth stating exactly: its two ends are `SolveFromPoint` and
`SolveToPoint`, **program options that the worksheet does not record**. The file does not say what
range SMath searched, the range decides which roots are found, and inventing one would invent the
answer.

`diff` is refused with its reason rather than as an unknown name. "The function `diff`" reads as a
gap somebody could close; *symbolic differentiation, which needs the CAS this engine deliberately
does not have* names the decision that closed it (§8.12).

**Effect across the three corpora.** Agreement **507 → 514**, comparable answers 537 → 544, markers
**1475 → 1450**, and four more worksheets now carry an answer that can be compared at all. **No new
disagreement**: everything the construct newly computes, it computes correctly.

**One agreement lost, and it was never real.** `7.3.sm` had `φ.1` agreeing at 20.3°. Its own
definition is a `solve`, which used to be a marker — so the display line below it showed a value
left over from an earlier region, and that stale value happened to match. Now the definition is live
and fails, because the worksheet builds its matrix with `identity`, which does not import. This is
§8.15's finding again, from the other side: **translating a construct moves failures onto the line
that actually has one**, and an accidental agreement is worth less than an honest failure. It is
also a signpost — `identity` is now the single name standing between `7.3.sm` and its eigenvalue
chain.

**The oracle cannot see this construct's characteristic answer.** SMath stores several roots as an
`n`×1 matrix, and the oracle compares scalars only, so those land under *stored answer unreadable*
rather than being scored. `CEE3500Test01Problem03.sm` is the clean example: Nomo computes
`[1.17307, 3.57795]` where SMath stored `mat(1.1731, 3.5779)` — right to every digit SMath kept, and
uncounted. 86 stored answers are unreadable for this and related reasons. **Teaching the oracle to
compare a vector against a stored matrix is the next measurement to make**, and it is worth making
before the next construct, because from here on the interesting answers are not scalars.

**A refusal must defer to the worksheet.** SMath resolves a document's own functions before its
built-in registry, and the importer's fallback already followed that order — but a refusal written
as a match arm sits *in front* of the lookup. `Finite differences.sm` writes `diff(y, x) ≡ 0`, a
stated equation whose left side is a call, which registers `diff` as a definition and is why every
`diff` in its documentation equations renders at all. The first version of this change refused those
five equations. All three refusals are guarded now, and the general rule is worth keeping in mind
wherever another one is added: **a name the worksheet defines is the worksheet's, whatever SMath or
Nomo also call it.**

### 8.26 The oracle learns to read a table (2026-08-28)

**Named as the next measurement in §8.25, and it was the right one.** SMath stores several roots as
an `n`×1 matrix, and the oracle compared scalars only — so the characteristic answer of the construct
just translated was counted *unreadable* rather than scored. Teaching it to compare element by
element moves **66 answers out of "unreadable"**: agreement **514 → 577**, comparable answers 544 →
610, and *stored answer unreadable* falls **86 → 8**.

The comparison is the same one, applied per element:

- Both sides flatten to a list of quantities, so a Nomo vector and a stored `mat(a, b, 2, 1)` meet
  as the same shape rather than being told apart by it. A scalar is a list of one, which is why the
  scalar path did not need a special case.
- **Each element states its own tolerance.** `mat(0.757, 1.74, 2, 1)` is one element written to
  three decimals beside another written to two, so one mantissa for the whole answer would be wrong
  for at least one of them. The emitter now records the first literal of each element alongside the
  answer.
- Different lengths are `ShapeDiffers` — a verdict, not a failure. It replaces `NotAScalar`, which
  had become the wrong name for the question: 21 answers land there, the interesting ones being
  `Newtoninterp.sm`, where Nomo computes one value against 30 stored, and the complex answers of
  `ElecEngExample.sm`, which evaluates but has no element-wise comparison yet. **Complex
  answers are the next extension of the same idea.**

**The boundary is inclusive, and that is not a widened tolerance.** Three answers were reported as
disagreements while being right: `7.2.sm` computes `337.5 mm²` where SMath stored `338 mm²`. Half a
unit in the last displayed place is exactly what those digits mean — SMath rounds half away from
zero — so a value sitting on the boundary belongs inside it, and it missed only because both sides
arrive as binary approximations of decimal strings and the subtraction lands a few parts in 10¹³
over. The comparison allows one part in 10¹² for that and nothing else: the nearest value that would
genuinely display as different digits is a whole unit away, which is *twice* the tolerance. After
it, agreement is **577 of 610** and the disagreements are 33.

**What the 33 disagreements are, and they are not new.** Six of them are newly *visible* rather than
newly wrong: `Broyden-method.sm` and `NewtonRaphsonApplications.sm` store vectors on lines whose
scalar neighbours were already disagreeing, and for the same reason — both fill their working
vectors with indexed assignment inside a loop, which does not import, so the line evaluates on a
placeholder. Every one of the 33 is in a worksheet that did not translate completely.

### 8.27 A derivative without a CAS (2026-08-28)

**The question this answers.** §8.24 closed `diff` as needing a computer algebra system, and that was
right about SMath and wrong as a conclusion about Nomo. SMath differentiates *symbolically* — the
expression goes to its CAS and another expression comes back. But the converter worksheet never
wants the
expression: `derivative_Mg` exists only to be sampled by a root search. What the worksheet needs is
the **value** of the slope at a point, and that is arithmetic rather than algebra.

**Forward-mode automatic differentiation.** Every value carries a second component — how fast it is
changing — and every operation carries the chain rule alongside the value it was already computing.
`(u·v)' = u'v + uv'` is a multiplication and two additions. Nothing is simplified, nothing is
rearranged, and no expression is ever built, so the "No CAS" commitment is untouched: this is the
same claim as `integral` being Simpson's rule rather than an antiderivative.

`crates/nomo-core/src/dual.rs` is the second numeric tower, joined to the arithmetic at exactly one
place — `Value::dual_pair`, written to the pattern `complex_pair` already established. Adding the
variant broke **eight** matches in the whole crate, which is the measure of how well that pattern
holds.

**It is exact, and that is the point.** A finite difference needs a step, and a step is a tuning
knob: the answer would depend on a number nobody could derive from the worksheet, with truncation
error at one end and cancellation at the other. This has none. Measured on the case that motivated
it — the peak of the converter worksheet's gain curve, where `Mg` is six functions deep:

| method | peak | distance from SMath's stored `61995.1263` |
|---|---|---|
| central difference, h = 1 | 61995.126350 | 5.04e-5 — **outside** the ±5e-5 the stored digits allow |
| central difference, h = 0.01 | 61995.126326 | 2.62e-5 |
| **automatic differentiation** | **61995.126327** | **2.69e-5** |

The finite differences bracket the answer and one of them misses; the exact method simply has it.
The residual 2.7e-5 is SMath's own display rounding — it wrote four decimals of a value whose fifth
is a 3 — and the two answers that follow, `Min_fsw` and `Max_Mg_calc`, land 4.0e-5 and 3.9e-5 from
stored values that allow ±5e-4.

**A missing rule is a refusal.** Only the operators and the elementary functions have rules. `floor`,
`round` and `sign` do not, and meeting one reports that it cannot differentiate rather than
answering: a derivative silently reported as zero because a rule was never written would be believed,
because zero is a plausible derivative. This is why the dual is a *variant* rather than a field on
`Quantity` — a field would default to zero and every unwritten rule would become a wrong answer, and
the type system would not say a word.

**Two judgements worth recording.** A comparison inside a derivative asks about the *value*, so a
piecewise definition differentiates on the branch its condition selects — exact everywhere except at
the switch, where the function has no derivative to be exact about. And `|u|` reports zero slope at
exactly zero, the symmetric member of the subgradient, rather than refusing an entire scan because
one of two hundred samples touched the axis.

**What it does not do.** Second derivatives — SMath's three-argument `diff(expr, var, n)` — would
need duals of duals, and nothing here nests. Vectors and complex numbers have no rules either: the
two towers meet nowhere, which the `dual_pair` promotion says by refusing rather than by silence.

### 8.28 `diff` translated, and the converter worksheet closes (2026-08-28)

**The importer's side of §8.27.** `diff(expr, x)` becomes `derivative(name, x)`, with the expression
lifted into a function unless it already is one. The converter worksheet's line

```text
derivative_Mg(f) : diff(Mg(f), f)     →     fn derivative_Mg(f) = derivative(Mg, f)
```

is the case that motivated all of it, and with it **that worksheet checks out completely: 34 of 34
stored
answers agree, `nomo check` exits zero, and the seven markers that remain are the seven this
document already listed as "not work"** — four decorative labels, two words of prose typed as maths,
and a date in the page header stored as arithmetic. The worked example that drove eight commits is
finished.

**Two guards, and one of them is the whole difference between the two readings of `diff`.**

- **The differentiand must read the variable.** `9.3.sm` writes `diff(y.B, t)` where `y.B` is a name
  the worksheet has already bound. SMath differentiates the *formula* that name stands for; Nomo
  would differentiate the *number* it evaluated to and answer zero. That is a wrong answer wearing
  the shape of a right one — the single outcome this importer must never produce — so a
  differentiand that never mentions the variable is the symbolic case and stays refused, with a
  marker that says exactly that. Two regions across the mechanics corpus are caught by it, and
  nothing legitimate is: `9.2.sm`'s whole kinematic chain — `v.x(t) : diff(x(t), t)` and then
  `a.x(t) : diff(v.x(t), t)` — translates.
- **An order above the first is refused by arity.** `diff(expr, x, 2)` would need a dual of a dual
  and nothing nests, so it is refused rather than approximated. The engine says the same thing from
  its side when a worksheet reaches it anyway: *a derivative of a derivative is not implemented yet*,
  which is what `9.2.sm`'s accelerations get.

**A shortcut, shared by three constructs and worth naming.** `int`, `solve` and `diff` each take an
expression where Nomo takes the name of a function, so each lifted the expression into one — and
`diff(Mg(f), f)` was becoming `fn slope_1(f) = Mg(f)` beside `derivative(slope_1, f)`, an alias for a
function that already existed. When the expression is nothing but a call to one of the worksheet's
own functions at the variable, that call *is* the function: `integral(f, a, b)`, `roots(Q, 0, 2)`,
`derivative(Mg, f)`. It reads as what the author wrote, and — the reason it is worth doing rather
than merely tidy — it puts the worksheet's own name on the line that reports an error instead of an
invented one, which is where a reader looks first.

**Effect.** Agreement **577 → 594** across the three corpora, comparable answers 610 → 627, complete
worksheets 17 → 18, and **no new disagreement**. Per corpus: 283 of 316 in the wiki corpus, 251 of
251 in the mechanics corpus, 34 of 34 in the converter worksheet.

**A hazard this shares with `int`, and does not close.** Lifting an expression out of a definition
loses that definition's *other* parameters: `df(x, μ, σ) : diff(f(x, μ, σ), x)` becomes
`fn slope_1(x) = f(x, μ, σ)` where `μ` and `σ` now resolve to the document's bindings rather than to
`df`'s arguments. Every corpus call passes the same names, so nothing is wrong today and the oracle
would say so if it were — but a worksheet that called `df(1, 0, 1)` with other values would get an
answer computed from the document's. `int` has had this since it was built. Closing it means
refusing the lift when the body reads an enclosing parameter, which needs the emitter to know what
definition it is inside.

### 8.29 `identity(n)`, one name and a whole chain (2026-08-28)

**The cheapest item on the list, and it was not small.** §8.25 named `identity` as the single name
standing between `7.3.sm` and its eigenvalue chain: the worksheet builds `I : identity(2)` and
everything after it — the eigenvalues by `roots`, the principal stresses, the angle between the axes
— failed on that one gap. Adding it took a dozen lines and took the worksheet from **27 of its
answers agreeing to 55, which is all of them**.

**What it is, from SMath's own strings rather than from the name.** `Text_ENG.lang`: *"Returns an
n x n identity matrix (a matrix of 0's with 1's along the diagonal). {0} must be a positive
integer."* All four corpus uses are one-argument, so the collision that caught `roots` (§8.24) is not
here — but it was checked rather than assumed, which is the point.

**Dimensionless, and that is the only thing it can be.** It exists to be multiplied by something
else. `det(S - λ·identity(2))` is the characteristic equation of a stress tensor, and it needs the
ones to take their dimension from `λ` — a matrix of `1 MPa` would make the subtraction work and the
determinant meaningless.

**The cap is on the elements, not on `n`.** `MAX_RANGE`'s own reasoning applies unchanged: a browser
tab has no way out of building a trillion-element matrix. A thousand rows is already a million
elements, and a worksheet that wants more has gone somewhere this tool is not for.

**Effect.** Agreement **594 → 610** across the three corpora, comparable answers 627 → 643, no new
disagreement. The mechanics corpus is at **267 of 267**. And `7.3.sm` supplies its own check: the
eigenvalues that `roots` finds numerically from `det(S − λ·I)` — −31.0977 MPa and 61.0977 MPa — are
the principal stresses the worksheet also computes in closed form four lines above, to every digit.

**A shadowing question, asked and answered.** `examples/matrix.nomo` bound a variable called
`identity` for the product `K·inv(K)`. A variable and a builtin function do not collide in this
language — `identity = 5` and `identity(2)` coexist — but an example that models the shadowing is a
bad example, so the binding was renamed and the example now uses `identity(2)` where it used to
write the matrix out.

### 8.30 The oracle reads a complex answer (2026-08-28)

**The last shape it could not compare.** §8.26 taught it tables and left 21 answers under *different
shapes*; six of those were complex — `ElecEngExample.sm` stores currents and powers like
`(14.88 − 9.47·i) A`, which evaluate perfectly and had no element-wise comparison. They have one
now, and it is the same comparison again: a complex value flattens to **real part then imaginary
part**, which is the order SMath writes them, so the machinery that compares a vector against a
stored matrix compares these without knowing they are complex.

**Each part states its own precision, and it has to.** `196.18 − 20.29·i` is five significant
figures beside four. One mantissa for the pair would scale the imaginary part's tolerance by
`|im/re|` — a factor of ten out on that answer — so the emitter records the literal of each part.
Finding them is structural rather than positional: the additive node whose right side mentions `i`,
which is robust to the unit sitting outside the whole thing, as in `(14.88 − 9.47·i)·A`.

**A complex answer against a real one is a shape difference, not an agreement.** An impedance is not
a resistance. Reporting *one value against two* says which, where comparing the real part and
ignoring the rest would quietly call it a match.

**Effect.** Agreement **610 → 616**, comparable answers 643 → 649, shape differences 21 → **15**,
and another worksheet checks out completely: `ElecEngExample.sm` is at 10 of 10.
No new disagreement.

**What is left under *different shapes* is not a reading problem.** All 15 are genuine: Nomo
computes 9 values where SMath stored 1, or 91 against 4, or 1 against 30. Those are worksheets whose
construct differs rather than whose answer is unreadable, and each is its own small investigation.

### 8.31 `diag(v)`, and a note on why it is here (2026-08-28)

**The evidence first, because it is unusual for this document.** `diag` appears in the SMath builtin
registry and **not once in 118 corpus worksheets**. Every other construct in §8 was ranked by how
much of the corpus it accounts for; this one accounts for none of it. It is here on the language's
own merits — the companion to `identity`, and what a worksheet reaches for when it writes a mass or
a scaling matrix — and the ranking says nothing either way. Recorded so that a reader does not infer
a corpus need that is not there.

SMath's own description settles what the name means where the corpus cannot: *"Returns a square
matrix containing on its diagonal the elements of the given vector (a vector is a column matrix)."*

**Two decisions worth the words.**

- **The zeros carry the diagonal's dimension.** `diag([3, 4] kg)` is `[[3 kg, 0 kg], [0 kg, 4 kg]]`,
  not a matrix with dimensionless zeros in it. The result exists to be added to and multiplied by
  other matrices, and a dimensionless zero beside `3 kg` would make every later operation report a
  mismatch against an element the worksheet never wrote. A vector of *mixed* dimensions is therefore
  refused here, where the reason can be stated, rather than one line further on where it cannot.
- **One direction only.** This makes a matrix from a vector and does not also read a diagonal back
  out of a matrix. Systems that overload the name decide by argument shape, so `diag(diag(v))`
  changes meaning with the shape of `v` — and SMath, where the name comes from, describes only this
  direction.

Nothing in the corpora moves, which is what zero uses means, and the baselines confirm it.

### 8.32 Strings, ranked by what worksheets do with them (2026-08-28)

**The corpus was asked first, and it answered narrowly.** 173 regions across 32 worksheets carry a
string operand, and 41 markers across 9 files were failing *because* of it. Reading them sorts into
four kinds:

1. **A verdict in words** — `msg : if(a ≤ a.max, "CASE(1) … Singly Reinforcement", "… Doubly")`,
   `b_type : "CASE 1 - Singly Reinforced Beams"`. The worksheet states its own conclusion.
2. **A label bound to a name** — `centroid.color : "red"`, `PNA.symbol : "+"`, and the `XYPlot'…`
   property names. Data the worksheet carries and Nomo has nowhere to *use*, but every reason to
   keep.
3. **A string-keyed lookup table** — the timber worksheet stores a grade table as
   `mat("Property", "C14", "C16", …)` and finds a column with `hlookup`.
4. **String manipulation** — `PolyProperties` formats numbers with `num2str`, `IsString`,
   `findstr`.

Kinds 1 and 2 are all of the 41 markers. Kinds 3 and 4 need collections of strings and a library of
functions on them, and neither is what this buys.

**So: a string value, and nothing else.** A literal between double quotes, bindable to a name,
choosable by `if`, comparable with `==`, and displayed. That is the whole feature, and it closes
**all 41 markers**.

What it deliberately does not have:

- **No arithmetic.** `"a" + "b"` is refused rather than concatenating. Concatenation is the tempting
  one and no corpus worksheet asks for it, so the operator keeps one meaning.
- **No order.** `<` on words would have to pick a collation — code point, locale, length — and every
  choice is a decision a worksheet cannot state. Equality has one answer, so equality is what exists.
- **No escapes**, and a string ends at its line. The missing closing quote is reported where it
  happens instead of swallowing the rest of the document.
- **Not inside a collection.** Vectors and matrices hold quantities, which is why `7.1.sm`'s stored
  `["1", "2", …]` is counted *unreadable* rather than compared — the same boundary complex numbers
  meet, reported the same way.

**It is a `Value` variant, not a `Quantity` with a flag**, for the reason `Dual` is: a string has no
dimension and no magnitude, so every operation that assumes one refuses it by construction instead
of by a check somebody has to remember to write.

**Effect.** The *"Nomo has no string values"* class goes from 41 markers to **zero**. Agreement does
not move, and should not have: these lines carry text, not numbers. Two stored answers become
visible as unreadable — the string vectors above — which is the honest accounting for a boundary
that is now reachable.

### 8.33 The second derivative (2026-08-28)

**The corpus asked for exactly one order.** 33 uses of `diff(expr, x, n)` across seven worksheets,
and every written `n` is **2** — accelerations in the mechanics corpus, and the inflection points of
a distribution in `normaldist.sm`. So the question was never "nth derivative"; it was "the second".

**Carried, not nested.** A dual of a dual would mean making the tower generic over its own component
type, which is a refactor of everything for a depth nobody asked for. Instead the dual gained a
second slot, and every rule gained its second-order term:

```
(u·v)'' = u''v + 2u'v' + uv''
(u/v)'' = u''/v − 2u'v'/v² − uv''/v² + 2uv'²/v³
f(u)''  = f''(u)·u'² + f'(u)·u''
```

That last one is the whole reason a second derivative is not the first one applied twice: the square
on `u'` is what a naive repetition drops. Every elementary function gained a third column — `sin`
its `−sin`, `atan` its `−2x/(1+x²)²`, and so on — written out because there is nothing here to
derive them with.

**Both orders come out of one evaluation**, and the second is carried even when only the first is
asked for. It costs a multiply and an add per operation, which is nothing beside evaluating the
expression at all; and a rule written only for the order somebody asked about is a rule that is wrong
the first time somebody asks about the other one.

**The ceiling is a number.** A third derivative would need a third slot and a fourth column in every
rule. Both are ordinary work and neither is written, so `derivative(f, x, 3)` says so — and the
importer refuses an order above 2, and an order the worksheet *computes*, rather than rounding either
down to what is available.

**Checked against hand-worked values** rather than against itself: `x⁴` at 3 gives 108, `ln` at 4
gives −1/16, `x^x` at 2 gives `4((ln 2 + 1)² + ½)` — the both-sides-varying rule, twice over — and a
Gaussian's second derivative at one standard deviation is **exactly zero**, which is the question
`normaldist.sm` asks.

**Effect.** The *"order above the first"* class goes from 23 markers to **zero**. Agreement
**616 → 621**, comparable answers 649 → 654, no new disagreement. `normaldist.sm` finds its mode at
`μ = 1` and its inflections at `[0.6, 1.4]` — `μ ± σ`, exactly where a normal distribution turns.

### 8.34 The CAS items, re-measured and costed (2026-08-28)

**Not a proposal.** §8.12 put computer algebra out of scope and nothing here reopens that. This is
the feasibility question asked properly, now that automatic differentiation, `roots`, `identity` and
strings exist and several things that *looked* symbolic have turned out not to be.

**First, the footprint is smaller than the name suggests.** `eval` is 71 calls across 18 worksheets
and reads like a CAS entry point; SMath's own string for it is *"Evaluate numerically"*. It is a
display directive. With it excluded, the idiom touches **21 of 118 worksheets**, in three groups:

| group | worksheets | stored answers | agreeing | not compared |
|---|---|---|---|---|
| `CustomFunctions` only — `Solve`, `Clear`, `at`, `Assign`, `Unknowns` | 10 | 158 | 30 | **128** |
| both | 7 | 120 | 26 | 94 |
| Maxima only | 4 | 157 | **112** | 45 |
| neither | 87 | 807 | 453 | 354 |

The last row of that table is the first finding: **"uses Maxima" is not "blocked by Maxima"**. Those
four worksheets already agree on 112 of their 157 answers; the Maxima call is incidental to them.
The block is the `CustomFunctions` idiom, and it is worth up to **128 answers in 10 worksheets** —
larger than any other single class left.

Inside those worksheets the markers are **77 free symbols** and **119 unknown-function markers for
the idiom's own names**. Both are the same thing wearing two hats, which the tiers below separate.

#### Tier 1 — the linear solve, which is not algebra at all

*(Corrected in §8.35, which measured what this section inferred: the numeric system solves are under
`FindRoot` and two-argument `roots`, not under `Solve`. The method below is right; the function name
it was aimed at was not.)*

Of the ten distinct `Solve` calls in the corpora, **eight are linear systems in their unknowns** by
inspection: `10.3_V.sm`'s three equations for the reactions `F`, `A`, `B`; `4.1–4.3.sm`'s six
support forces; `7.1–7.2.sm`'s single equation for a neutral axis. That is what statics *is* — ΣF =
0 and ΣM = 0, solved for reactions.

A linear system needs no symbol manipulation. It needs its coefficients, and those come out of
**evaluating the residual**: `b = −r(0)`, and column *j* of the matrix is `r(eⱼ) − r(0)`. Demonstrated
with nothing but today's parts — a residual written as three functions, `inv`, and a matrix product:

```
K = [[1, 0, 1], [0, 1, 0], [-1, -1, 1]]
inv(K)·b = [-39.05 N, 98.1 N, 59.05 N]
```

which is the hand-worked answer. **No derivatives are needed** — the Jacobian of an affine map is
recoverable by subtraction — so this needs neither a CAS nor even the AD that arrived in §8.27.

And linearity is **testable rather than assumed**, which is what lets it into this project at all: an
affine residual satisfies `r(x+y) − r(x) − r(y) + r(0) = 0`. Probed on the system above it returns
exactly `0 N`; probed on a residual containing `F·A` it returns `15 N²`. A system that fails the
probe is refused, and says why.

What it would cost: one engine function that evaluates a residual at zero and at the unit vectors,
probes affinity, and returns `inv(A)·b`; and an importer lift of `Solve(sys(…), sys(unknowns))` into
a residual function of those unknowns — the same lift `int`, `solve` and `diff` already perform. No
new concepts.

#### Tier 2 — formula-valued names: one architectural decision, still not algebra

The deeper blocker is not the solve. It is that **SMath lets a name hold a formula in an unbound
variable**. `Clear(t)` — 54 calls across 24 worksheets — exists precisely to make a name free again;
then `x.S : ½·x.A` holds an expression in `t`, and `diff(x.S, t, 2)` and `at(B(t), t ≡ 3 s)` operate
on that expression. The 77 free-symbol markers are this, and it is why `10.3_V.sm` is blocked well
before its linear solve is reached.

Nomo has no free symbols by design (§8.20) — but it has functions, and §8.22 already established
that a parameter can be *inferred*: a definition free in `x` that a plot draws is a function of `x`.
Generalising that from "that a plot draws" to "whose free variable a later region differentiates,
substitutes into, or solves for" turns `Clear(t)` … `x.S : …t…` into `fn x_S(t) = …`, after which
`diff(x.S, t, 2)` is `derivative(x_S, t, 2)` — built in §8.33 — and `at(B(t), t ≡ 3 s)` is a function
call.

No expression is ever manipulated; a name is given a parameter it did not declare. That is feasible
with what exists. What it costs is a **decision, not a technique**: whether a Nomo worksheet accepts
that a name can be a function of a variable nobody wrote down. §8.22 is a precedent for exactly one
narrow case, fenced by four conditions; this would widen the same inference considerably, and it
would need fencing of the same kind.

#### Tier 3 — genuine algebra, and it stays out

- **A symbolic *answer*.** `5.1.sm` stores `x.0 ≡ L·(−3 + √39)/6` — an expression, not a number.
  Producing that needs a CAS. Worth noting that the same worksheet solves the same equation
  numerically two lines later and gets `1.08 m`, so nothing the engineer wanted is lost.
- **`simp`, `ratexpand`, `assume`, and the Maxima calls** — simplification, expansion, assumptions:
  42 calls across 11 worksheets. §8.12's judgement stands unchanged.
- **Symbolic integration**, which no corpus worksheet asks for numerically-unreachably.

#### The conclusion

"CAS" in this repository's notes has been covering three different things, and only the third is a
computer algebra system. Tier 1 is the largest cheap win left in the importer and involves no algebra
by any definition. Tier 2 is a product question about how far a name may be re-read, and the
technique it needs is already built. Tier 3 is correctly and permanently out.

### 8.35 `solve_linear`, and a correction to §8.34 (2026-08-28)

**The method held; the target did not.** §8.34 costed the linear solve and pointed it at `Solve`.
Building it turned up the check that section should have made: **not one `Solve` in the corpora
stores a numeric answer.** Four store a symbolic one and eighteen store none at all.

The reason is worth stating, because it is the difference between the tiers. A system being *linear
in its unknowns* is not enough — its **coefficients** must be numbers, and in these worksheets they
are not. `4.1.sm` clears `S.1…S.6` *and* `F` and `a` before solving, so `Solve(GGB, R)` answers
`S.2 ≡ −F, S.3 ≡ −9F/2, …`: expressions in a symbol. `10.3_V.sm` solves for `F`, `A`, `B` while `t`
is cleared, and the answers come back as functions of `t` — the worksheet then calls `F(t)`. **Tier 1
is downstream of Tier 2 wherever the coefficients are symbolic**, and §8.34 did not see it.

**Where the numeric shape actually lives.** The same worksheets solve the same systems numerically
too, and under other names: **`FindRoot(system, guesses)` — 16 numeric stored answers — and
two-argument `roots(system, unknowns)` — 4 more.** `4.1.sm` is the clean demonstration: it solves one
statics problem five ways, and the numeric ones (`roots`, `FindRoot`) store vectors of numbers where
`Solve` stores expressions. Those 20 answers are Tier 1's real target, and they are numeric on both
sides, so the oracle can score them.

Better still, `FindRoot`'s second operand is a vector of **guesses carrying units** —
`sys(A·N, B·N)` — which is exactly the dimensional information the solver needs and the importer
could not otherwise supply.

**What was built.** `solve_linear(f, kinds)`, where `f` is a residual in the unknowns and `kinds`
names them by dimension:

```nomo
fn balance(F, A, B) = [F + B - mass*acc, A - mass*g, B - F - A]
solve_linear(balance, [0 N, 0 N, 0 N])   ' [-39.05 N, 98.1 N, 59.05 N]
```

- **The coefficients come out of evaluation.** `b = −r(0)`, and column `j` is `r(eⱼ) − r(0)`. No
  expression is manipulated and no derivative is taken: the Jacobian of an affine map is a
  subtraction.
- **Dimensions come off and go back on exactly.** A moment equation beside two force equations makes
  the matrix mixed by row, which `inv` refuses and is right to. Everything is in base SI, so scaling
  by one unit of each dimension multiplies by exactly 1.0 and changes no bits; the dimensional check
  is not lost, because the residual subtractions still refuse to take a force from a moment.
- **Linearity is checked on the answer.** The solution is put back into the equations, and a row that
  does not balance to one part in 10⁹ of its own largest term is refused. That is a stronger
  statement than probing for affinity — *this is the solution*, not *this looked affine at three
  points* — and it is what lets a caller who cannot verify linearity, such as an importer reading
  somebody else's worksheet, use it without guessing.
- `kinds`' magnitudes are never read. The engine needs to know the first unknown is a force, not
  what force it might be.

**The correction is the finding.** §8.34's method survives intact and its arithmetic was
demonstrated before this was written; what it got wrong was assuming that the construct named
`Solve` was the one wanting a numeric solver. The corpus said otherwise the moment it was asked a
more specific question.

### 8.36 The importer half of Tier 1 has no target, and why (2026-08-28)

**A negative result, measured.** §8.35 built `solve_linear` and named `FindRoot` and two-argument
`roots` as the importer's target — 20 numeric stored answers. Writing that mapping needs one thing:
the call must say **which names are the unknowns**, so the equations can be lifted into a residual
function of them. Every system-solve region in the corpora was checked against that requirement, and
**none of the ten passes it**:

| region | why not |
|---|---|
| `4.1.sm` `FindRoot(GGB, sys(F,…))` | unknowns `S.1…S.6` are free symbols *inside* `GGB` |
| `4.2.sm` `FindRoot(GGB.nu, sys(A.x ≡ G, …))` | same — the system is a name |
| `4.3.sm` `FindRoot(GGB, Vars, 1e-16)` | same, plus a convergence tolerance |
| `4.2.sm` `roots(GGB.nu, R.nu)` | same, and the unknowns carry no dimension either |
| `5.2-4.sm` `FindRoot(sys(M(L) ≡ 0, Q(L) ≡ 0), sys(A ≡ N, B ≡ N))` | `A` and `B` are free *inside* `M` and `Q` |
| `9.1.sm` `FindRoot(v.2(t) ≡ v.2E, t.2E ≡ 1 s)` | the name declared unknown is not the one the equation uses |
| `5.1.sm` ×2, `5.2-4.sm`, `9.3.sm` | **liftable** — and single-unknown, with a nonlinear equation |

The split is clean and it is the same line as everywhere else in this investigation. **Every
multi-unknown system keeps its unknowns as free symbols inside another name**, which is Tier 2, not
Tier 1. **Every region the importer *can* lift has one unknown and a nonlinear equation** —
`5.1.sm`'s `Q` is a quadratic shear force, `9.3.sm`'s `x.A` is a quadratic position — so
`solve_linear` would correctly refuse them.

**And they cannot be sent to a root finder either.** `FindRoot` solves from a starting guess, and
*which* root that finds is the method's choice rather than the worksheet's: `5.1.sm` starts at `L`
and gets `1.08 m`, and starts at `L/2` — nearer the other root — and gets `-3.08 m`. Reproducing that
choice would mean reproducing the algorithm, and unlike `solve` (§8.24) the Nonlinear Solvers plugin
is **not on this machine** to be read. Nomo's own methods are a bracket and a window scan, and the
call supplies neither.

**So the mapping is not written, and the refusals now say why.** 18 `FindRoot` regions reported as
*the function `FindRoot`* — an unknown name, which reads as a gap somebody could close. They now
report the method's choice of root; and `roots(system, unknowns)` reports the missing dimensions
rather than being lumped in with the guess-based form it shares a name with. That is the §8.25
pattern: a refusal that names the decision is worth more than a refusal that names the function.

**What this leaves.** `solve_linear` stands on the language's own merits — statics is what it is for,
and `examples/numerics.nomo` shows it solving one. Its importer half waits on Tier 2, exactly as
`Solve` does. Three separate constructs — `Solve`, `FindRoot`, `roots` of a system — have now each
been followed to the same wall: **a name in these worksheets can hold a formula in a free symbol, and
in Nomo it cannot.** That is one decision, and it gates all of them.

### 8.37 Tier 2 attempted, measured, and reverted (2026-08-28)

**What was tried.** §8.34's Tier 2 said a name holding a formula in a free variable could become a
function, generalising §8.22's narrow rule — *a definition free in `x` that a plot draws is a
function of `x`* — to *a definition free in one variable that anything later differentiates,
substitutes into, or plots*. The machinery was built: a fixpoint closure over definitions, a global
rewrite of every use into a call, and `diff`/`at`/plot as triggers. It was measured against every
worksheet and **reverted**.

**It regressed six worksheets, in three independent ways**, and each way is worth recording because
each is a property of the inference rather than a bug in one line of it.

- **"Free in the document" is not "has no value here".** §8.22 tests, at emission, whether `x` has a
  value *at that point in the page*; the generalisation tested whether the name is bound *anywhere*,
  which `Bound` answers for the whole document and which counts a function's parameter as a binding.
  `fdist.sm` has an `x` parameter elsewhere, so its `liner` — a working function of `x` since §8.22 —
  stopped being one. Two tests that look interchangeable and are not.
- **The closure reaches things that are not formulas.** `7.1.sm`'s `P : augment(y.r/mm, z.r/mm)` is a
  *table* that a plot draws. Its columns depend on `z.N`, which is declared symbolic, so the
  transitive rule made `P` a function of `z.N` and turned a working line into a marker. §8.22 avoided
  this with a condition the generalisation dropped — *nothing else reads it* — which is exactly what
  separates "a curve named before drawing" from "a table computed from a symbol".
- **A definition can read itself.** `NewtonRaphsonApplications.sm` writes
  `global x : [x[1], x[2], …, x[n]]`, so `x` reads `x`; the closure made `x` a formula in `x` and
  every later mention a call to it.

**And a fourth thing, found while narrowing.** Tightening the variable to those the worksheet
`Clear`s — SMath's own declaration, which ought to be the strongest evidence available — did not
help enough: `6.3.sm` clears `β`, and the rewrite then reached definitions whose emission had already
failed, so the body called a function nothing had written. Candidate and emitted are two different
sets, and every use site has to consult the second; §8.22 already knew that
(`curves` versus `curves_emitted`) and the merge lost it.

**What the prize would have been.** Small. Only three worksheets `Clear` exactly one name — `10.3_V`
(`t`), `6.3` (`β`), `8.3` (`F`) — and `10.3_V`'s chain feeds a symbolic `Solve` that stays out of
scope whatever happens here. The reachable win is `6.3.sm`'s two answers, twice over for the two
editions: **about four**.

**The conclusion, which is a design finding rather than a defeat.** §8.22's rule is narrow *because*
each of its four conditions is load-bearing, and the generalisation dropped or weakened three of
them. A wider inference is still possible — it wants to be a **second, separately fenced rule**
rather than a widening of the first, and it wants the emission-time tests §8.22 uses rather than the
document-wide ones. That is a larger piece of work than its four answers justify today, and it is
recorded here so the next attempt starts from the three failures rather than rediscovering them.

### 8.38 SMath's summation, and the capture it exposed (2026-08-28)

**`sum(expr, i, a, b)` needed no new builtin, only a lift.** SMath spells a summation as a function
of four operands — the summand, the index's name, and the index's first and last values — and the
corpora hold **77 of them across 14 worksheets**, against three of the one-argument `sum(v)`. It is
`int`'s shape exactly (§8's checklist item on the integral), and it translates the same way: the
summand is lifted into a named definition, because Nomo's `map` takes the *name* of a function and
the language has no lambdas. What is different is that nothing had to be added to the engine —
`map` over a `range` supplies the index and the one-argument `sum` is the fold, so

```
Q.x ← sum(el(x̄, i, 1)·el(b, i, 1)·el(h, i, 1), i, 1, rows(h))
```

imports as

```nomo
fn term_5(i) = x_bar[i, 1]*b[i, 1]*h[i, 1]
Q_x = sum(map(term_5, range(1, rows(h))))
```

SMath's index steps by one, which is what a two-argument `range` does — the three-argument form,
whose meaning here is still unverified (§8's `range` refusal), is not needed and is not used. `i` as
an index name needed nothing either: a parameter shadows the imaginary unit, so the four lines that
used to read *an index must be a whole number, found a complex number* are the same four that now
answer.

**What it was doing before is the more interesting half.** `sum` is in the built-in registry, so a
four-operand call was passed straight through and spelled `sum(expr, i, a, b)` — four arguments to a
function that takes one, with `i` reading as the imaginary unit. That fails at *evaluation*, not at
import, so it left no marker: the worksheet imported clean and then would not run. This is the
failure mode §8.20 named in a different place, and the registry lookup is where it hides — a name
Nomo also has passes the "is this known?" test on its name alone, arity unchecked.

**Measured.** Agreement went from 289 to 291 of the wiki corpus and from 269 to 283 of the
mechanics one — **558 to 574** — with the mechanics corpus still at 100% of what it can compare.
`7.2.sm` went from 7 answers agreeing to 13 in both its editions; `financial.sm` from 10 to 12;
`Calc Area Properties…sm` from 2 to 6, and from 16 unevaluated lines to none.

**`product` is the same shape and is deliberately not translated.** Nomo has no `product` fold, the
corpora hold **two** calls in one worksheet, and that worksheet stores no answers and is blocked on
`range` with a step regardless. There is nothing to measure, so the marker stands.

#### The capture, which is why this took a guard as well

A lifted helper is written *above* the definition it came out of. Where that definition is a
function, the names in the helper then resolve to the worksheet's **globals** rather than to the
parameters that were in scope where they were written, and Nomo has no closures to fix it with.

`simpsonrichardson.sm` is where this stopped being theoretical. Its Simpson rule is
`simp(a, b, h, n) : … sum(f(a + k·h), k, 1, n−1) …`, and the summand lifts to
`fn term_1(k) = f(a + k*h)` reading the *global* `a` and `h`. That worksheet calls `simp` with
exactly those globals, so the first answer comes out **right by coincidence** — which is the worst
way for an answer to be right, and the reason this is a refusal rather than a warning.

`7.1.sm` shows the same thing without the coincidence. Its polygon area is
`A(y, z) : sum(A(y, z, j), j, 1, n(y))`, and the unguarded import produced

```nomo
fn term_1(j) = A(y, z, j)          ' y and z are A's parameters, not the document's
fn A(y, z) = sum(map(term_1, range(1, n(y))))
```

where `y` and `z` are defined thirty lines further down as *different* vectors — the centroidal
coordinates rather than the reference ones. Five answers agreed out of a document that also called a
three-parameter function with two arguments.

**The guard is general, and it was not only `sum` that needed it.** Every construct that lifts —
`int`, `sum`, `solve`, `diff`, and the `for` loop that becomes a `map` — now refuses when the body
being lifted reads a parameter of the definition it sits in, and says which parameter. `diff` had the
bug already: `normaldist.sm`'s `df(x, μ, σ) : diff(f(x, μ, σ), x)` was lifting `fn slope_1(x) =
f(x, μ, σ)` over the globals, in a worksheet that **redefines `μ` and `σ` halfway down the page**.

**It costs nine agreeing answers, and that is the right trade.** Four in `normaldist.sm`, four in
`7.1.sm` across its two editions, one in `financial.sm` — every one of them produced by a document
that reads a name it does not mean. The rule this repository works to is that a construct which is
right most of the time is worse than one that reports it cannot tell, and a coincidence is the
weakest form of "most of the time" there is.

#### What the summation exposed next, with the evidence for it

`Calc Area Properties of Composite Rectangular Areas.sm` now evaluates every line it has, and **13
of its 21 answers report a different shape**: Nomo computes nine values where SMath stored one. All
thirteen descend from one line, `A.total ← b·h`, where `b` and `h` are both `mat(…, 9, 1)` — two
columns of nine.

The file settles what SMath means by it. The stored answer is **64 in²**, and
Σ bᵢ·hᵢ = 96·0.5 + 4·(4·0.5) + 4·(4·0.5) = 64: SMath's `*` between two columns of the same length is
the **dot product**. Nomo's is element-wise, deliberately and documented (`docs/language.md`, "*is
element-wise between two vectors*… use `dot(a, b)` for an inner product"), because that is what a
tabulated calculation wants — so this is an importer mapping, not a language question.

It is not written, because the importer would have to know an operand's *shape* to know which `*` it
is, and it currently knows only names. That is a real piece of work — the emitter would have to track
which names are bound to a `mat` and with what rows and columns — and it wants SMath's own answer for
the cases the corpus does not show (row times row, column times row) rather than an inference from
the one case it does. Recorded here with the evidence so it starts from `64 in²` rather than from
scratch.

### 8.39 `·` between two columns, read out of the numeric assembly (2026-08-28)

§8.38 ended by naming this and refusing to guess the rest of the rule. `/opt/smath` settles it, and
`SMath.Math.Numeric.dll` is where the answer is.

**`TMatrix::op_Multiply(TMatrix, TMatrix)` branches three ways, and the first is the surprise.**
Before anything else it tests three things — `c2` has one column, `c1` has one column, and the two
have the same number of rows — and when all three hold it runs

```
Σᵢ c1[i,0]·c2[i,0]
```

and returns it as a **scalar**. Only if that fails does it test `c1.cols == c2.rows` and do the
ordinary matrix product into a `c1.rows × c2.cols` result; and only if *that* fails does it throw
(`GeneralException(Errors 61)`). Which array dimension is rows and which is columns is not left to
reading: the matrix-product branch indexes `c1[i,k]·c2[k,j]` with `k` running to `c1.GetLength(1)`,
so `GetLength(0)` is rows.

**So SMath's `·` and Nomo's disagree in exactly one case.** Two columns of the same length: SMath
takes the inner product, Nomo multiplies element-wise. Everything else already agrees — matrix by
matrix, matrix by column, and a scalar broadcast all mean the same thing in both — and Nomo's
element-wise reading is deliberate (`docs/language.md`: *"`*` is element-wise between two vectors of
equal length, which is what a tabulated calculation wants"*), with `dot(a, b)` for the inner product.
It is an importer mapping, and now it is written.

**The importer knows shapes only where the file states them, which is enough.** `Emitter::shape_of`
sees through four things and no more: a `mat(…, r, c)` literal with literal shape operands, a name
bound to one, a `transpose` of either, and scaling — because `transpose(mat(…, 1, 11))·mm` is how a
worksheet writes a column of millimetres. Anything else is `None`, and `None` means leave `*` alone.
A name is dropped from the map when it is rebound to something whose shape is unknown, and a
function's parameter shadows the global of its name, so a body cannot read a shape that is not its
operand's.

**Measured, and it is narrow by construction.** Across both corpora exactly **18** multiplications
have a stated shape on both sides: 13 are matrix products, which both languages already agreed on,
and **five are column·column of equal length**, which is what changed. That is the whole footprint.

**What it bought.** `Calc Area Properties of Composite Rectangular Areas.sm` — one of the five
*different shapes* investigations §8.38 inherited — is **finished**: 19 of 19 comparable answers
agree, from 6, and the two that remain are stored answers the oracle cannot read. All thirteen of its
shape mismatches were `A.total ← b·h` and the chain below it. Wiki agreement went 291 → **304**, and
the wiki corpus's shape mismatches fell from 15 to **2**, both of them `Newtoninterp`.

**Two things found while looking, neither of them work.**

- **There is no row-times-column anywhere in either corpus.** SMath would treat `1×n · n×1` as an
  ordinary matrix product and answer with a 1×1 *matrix* rather than a scalar, which is a different
  thing from the first branch — and the emitter flattens a single row and a single column to the same
  Nomo vector, so it could not tell them apart anyway. Zero uses, so nothing is written for it.
- **`CEE3030Fall2009SolutionTest2.sm` writes binomial coefficients as 2×1 matrices**, because a
  stacked pair in parentheses is what `⁽ⁿₖ⁾` looks like. `mat(6, 2, 2, 1)·mat(14, 8, 2, 1) /
  mat(20, 10, 2, 1)` is the hypergeometric pmf drawn, not computed: the region stores **no answer**,
  and SMath evaluating it would do the same matrix arithmetic Nomo now does. Reading it as a
  binomial coefficient would be inventing an operator the file does not contain.

**And one that is.** `10.5.sm` now says why it cannot answer instead of answering the wrong shape.
Its `F ← [0, M₀, F₀, 0]` holds a moment beside a force, and `γ` holds a dimensionless ratio beside a
reciprocal length, so the products are all forces — except that the literal `0` is dimensionless in
Nomo and the fold refuses to add it to a newton. Two lines moved from *different shapes* to *did not
evaluate*, which is the same wrongness stated honestly, and the blocker behind them is now visible
and named: **a vector whose elements carry different dimensions, with a bare zero in it**. That is a
question about Nomo's arithmetic rather than about the importer, and it is not answered here.

### 8.40 A CAS, costed against the built engine (2026-08-29)

**Not a proposal, and the third time this has been asked.** §8.12 settled the scope decision against
the corpora; §8.34 costed the items *before* automatic differentiation, `roots` and `solve_linear`
existed. This asks it against the engine as built, and measures the blast radius rather than
estimating it. The scope decision is unchanged. Two of §8.12's supporting claims are not, and the
corrections are the reason this section exists.

**"CAS" is four separable layers and they do not cost the same.**

| layer | what it is | cost |
|---|---|---|
| **A** Symbolic values | free names in the value tower, substitution, printing | small — measured below |
| **B** Symbolic differentiation | `d/dx` over the AST | small; §1's "roughly a weekend" holds |
| **C** Symbolic linear algebra | exact solve over symbolic coefficients — §8.12's parked item | **larger than §8.12 says** |
| **D** Rewriting | `simp`, expand, factor, symbolic integration | incompatible with §9's gates |

#### What the architecture makes cheap, measured

A `Value::Symbolic(Box<Expr>)` variant was added and the workspace compiled, to count what a fourth
tower actually touches. **Nine distinct exhaustive-match sites break, workspace-wide** — seven in
`value.rs`, one in `render/mod.rs`, one in `golden.rs`. Nothing in `eval.rs`, `doc.rs`, `graph.rs`,
`nomo-wasm` or `nomo-smath` fails to compile. That is not luck, and three existing decisions are why:

- **`complex_pair` and `dual_pair` are the pattern, already instantiated twice.** Their own comment
  states it — *a second numeric tower joins the arithmetic at one place rather than at every
  operator*. A `symbolic_pair` is the third instance of a shape the file already carries.
- **The trace and the AST already keep what a symbolic layer needs.** §5 keeps expression structure
  with spans to render time, and `ast.rs` retains semantically redundant syntax — `Paren`,
  `ImplicitMul` — expressly so the symbolic column reproduces what was written. Displaying a
  symbolic result needs no new rendering architecture.
- **There is no `HashMap` in `nomo-core`.** Ordering is `BTreeMap` and `BTreeSet` throughout, so the
  canonical term ordering a symbolic layer needs would inherit a deterministic container discipline
  rather than introduce one.

Layers A and B are feasible at roughly one to two weeks, without touching the numeric path.

#### What blocks it, ranked

**1. A free symbol has no dimension, and dimensional analysis is the product.** Every `Quantity` is
`Copy`, in base SI, with its dimension known when it is built. `x + 1 m` cannot be decided without a
dimension for `x`. The two ways out are inference — unification over an abelian group, a subsystem
rather than a weekend — or declaration. **The declaration convention is already in the tree**:
`solve_linear(f, kinds)` takes a vector whose *dimensions* name each unknown and whose magnitudes
are never read (§8.35). A symbolic layer should reuse exactly that rather than invent a second way
to say the same thing.

**2. The linear algebra that exists cannot be reused, and "bounded and well understood" does not
survive it.** `Value::det` and `Value::inv` are Gaussian and Gauss-Jordan elimination **with partial
pivoting by magnitude, ties broken by the lower row index**. A symbolic matrix has no magnitude, so
that code is structurally unusable for layer C, which needs fraction-free (Bareiss) elimination and
a **zero-test on the pivot**. Over exact rationals that test is decidable. Over this engine's `f64`
coefficients mixed with symbols it is a *heuristic* — and a heuristic zero-test yields exactly the
failure this project refuses everywhere else: an answer that is quietly wrong, in the one place
nothing downstream can catch it. **This is where a bounded symbolic solve becomes an unbounded one.**
§8.12 called the parked capability bounded and well understood; the boundedness was assumed rather
than measured, and it holds only if the coefficient field is exact.

**3. Rewriting contradicts the reduction-order invariant head-on.** §3 makes reduction order part of
the language — nodes are `a + i*step` rather than repeated addition, and an iteration applies one
step at a time, *because reassociating would show in the last bits*. Reassociating is a simplifier's
entire job. Layer D is survivable only under a rule decided up front: **the symbolic layer never
feeds a rewritten expression into numeric evaluation without the rewrite being visible.** Discovered
later rather than decided first, that is a rewrite of the engine.

**4. A byte-exact gate and an open-ended rule set pull against each other.** §9's first gate compares
Nomo's own output bit-exactly and is never loosened. Symbolic output falls under it, so the canonical
printed form must be frozen — and every simplification rule added afterwards churns snapshots. A
CAS's rule set is open-ended by nature. Workable only if the symbolic surface is closed and versioned
like a language feature, which is the opposite of how these systems are usually grown.

**5. Tower interactions grow faster than the towers.** Complex-in-a-collection and
differentiating-through-a-matrix are both deliberately unbuilt and say so by name. A fourth tower
multiplies the combinations that must each be either built or refused.

**Not a blocker: size.** The artifact is 649 KB today and a hand-written symbolic core is tens of KB.
The trap is the other direction: there is no mature `no_std`, no-I/O, deterministic Rust computer
algebra crate, so this is build-your-own and maintain-forever, and anything vendored would have to
pass `check-no-host-math.sh` before it is even a candidate.

#### The demand side, which is the decisive half

- **The representative corpus says about 2%.** One CAS-like call in 54 wiki-corpus files (§8.12).
  The 7.7%-of-regions figure comes from the corpus written by SMath's principal plugin author, which
  measures expert capability rather than field usage.
- **Twice now the CAS-shaped requirement has dissolved into exact numerics.** `diff` became
  forward-mode AD with no step size (§8.27, §8.33); the statics solve became coefficients recovered
  by residual evaluation (§8.35). Neither needed algebra and both are exact.
- **The one attempt was built and reverted for four answers** (§8.37).
- **`5.1.sm` is the tell.** It stores the symbolic root `L·(−3 + √39)/6` and then solves the same
  equation numerically two lines later and uses `1.08 m`. The engineer wanted the number.

#### The conclusion

**Do not add one**, and the reason is not effort — layers A and B are cheap and now measured. It is
that a CAS attacks the differentiator. Bit-reproducible dimensioned numerics is what this project has
and a general-purpose algebra system does not; a CAS is where the comparable projects gave that away,
EP by handing the sheet to SymPy on a server, which is the architecture §2 exists to refuse.

**If a door is to be kept open, it is layer A alone, fenced**: symbols declared with a dimension by
the `kinds` convention, substitution, and a symbolic `derivative` shown *beside* the AD number rather
than instead of it — with no rewriting whatsoever. Nine match sites, one new tower, no change to the
numeric path, and it stops short of the pivot zero-test, which is the actual cliff.

The trigger for reopening is unchanged from §8.12 and is a demand question, never a capability one:
evidence from the target user's own files, not from the corpora.

### 8.41 A worksheet's prose is Markdown (2026-08-29)

**Decided: the text of a comment is Markdown, and it is a rendering concern only.** Headings,
paragraphs and lists to begin with, in a subset that is closed and written down rather than "as much
CommonMark as fits". Nothing about the language changes — not the lexer, not the AST, not the graph.

**What makes it nearly free is a decision already taken.** `lex.rs` keeps a comment as a token rather
than discarding it, and `eval.rs` gives it an `Outcome` with a span, *because a worksheet's prose is
part of its output* (§5). Prose therefore already arrives at the renderer as an ordered run of lines
with source positions on them, which is exactly the input a block parser needs. Markdown is read
there and nowhere else.

**It also fixes something that was wrong.** `render/html.rs` emits one `<p class="prose">` per source
line, so a paragraph wrapped across five lines renders as five paragraphs — visible in
`tests/golden/llc.snap`, where a six-line introduction is six `<p>` elements. Joining a run of lines
into one paragraph is the first thing a block model does.

#### The blocking rule

A run of consecutive `Comment` outcomes **on consecutive source lines** is one block run. A
statement, a blank source line, or an empty `'` ends it. Both terminators are already legible: a
blank source line produces no outcome at all, so the gap shows in the spans the outcomes carry, and
an empty `'` produces an empty comment, which is Markdown's own paragraph separator anyway.

That rule keeps the whole thing inside the renderer. The parser, the document layer, the dependency
graph, the version pragma and the resource trailer are untouched, and a build that renders prose as
flat lines still renders every worksheet — the property §7 asks of any format change.

#### The subset, and why each exclusion is not timidity

| In | Out |
|---|---|
| ATX headings `#`…`######`, space required | setext headings, `---` thematic breaks |
| paragraphs, soft-wrapped lines joined | indented code blocks |
| bullet lists `-` `*` `+` | block quotes, fenced code, tables |
| ordered lists `n.` `n)` | raw HTML |
| the existing `' image <name> [WxH]` line | inline emphasis, links |

- **`---` collides with the format.** `' --- resources ---` is the trailer sentinel, and a setext
  underline would additionally promote any paragraph followed by a line of dashes into a heading.
  A worksheet must never acquire a section break by writing about a range of values.
- **Indented code is the one measured hazard** — see below. In a worksheet, leading whitespace on a
  prose line is a wrap, not a program.
- **Raw HTML passthrough is an injection path.** `body()` escapes everything it emits and the browser
  front end assigns the result to `innerHTML`. The renderer keeps escaping everything.
- **Inline emphasis is deferred, and `_` should never be built.** 106 corpus prose lines carry two or
  more underscores and every sampled one is an identifier — `fn qq_at_1(k) = 448.83*xx[k]`, a line
  the importer commented out. Underscore emphasis would eat variable names in the one kind of prose
  this project has most of. If inline is ever wanted, `` ` `` and `**` only.

**One escape, for humans rather than for the importer:** a backslash before a leading marker,
`' \# not a heading`. The measurement below says the importer needs to escape nothing.

#### What real prose actually contains

Measured rather than assumed: `smath-import` over all 114 worksheets of both corpora, 6088 prose
comment lines outside the trailers, counting lines that begin with a Markdown block marker.

| leading marker | lines | what they are |
|---|---|---|
| `- ` | 76 | genuine bullets — `- perimetro`, `- area`, `- momenti di inerzia` |
| four spaces | 43 | **wrap continuations** — `    to the top-most fiber)` |
| `1.`–`6.` | 24 | genuine numbered steps — `1. The matrix, T, below contains a table of values.` |
| `* ` | 3 | genuine bullets — `* Trash screen:` |
| `#` | 0 | — |

**103 of the 143 hits are lists that Markdown renders correctly**, which is the case for doing this
at all: the prose in these files is already written as Markdown by people who were not writing
Markdown. The remaining 40 are the reason indented code blocks are out of the subset, and dropping
them from the subset costs nothing anyone will miss — a worksheet that wants a program has statements.

Two further things the corpus settles. The importer's own markers read `' [import] unsupported: …`,
which begins with `[` and is inert under every construct listed above. And `examples/interlock.nomo`
numbers four steps with math *between* them, so each item is its own single-item list rather than one
list of four — which is what the file means, and it is worth knowing that it renders as `<ol start=n>`
by design rather than by accident.

#### The image line stays as it is

`' image <name> [WxH]` is recognised as a block before Markdown sees the line, and `![alt](name)` is
not added. The reason is the size: §8.19 argues that how large a figure was drawn is *placement*, part
of what the author decided, and Markdown's image syntax has nowhere to put it. A second syntax that
could express only the weaker half of the existing one would be a way to lose the layout by accident.
A caption, if one is wanted, extends the line that already carries the placement.

#### Two things about the frame, both settled by building it

Both were written down as open questions and both were closed by the renderer, one of them because
grouping forced it.

- **`' nomo 1` is no longer rendered.** It was a paragraph reading "nomo 1" at the head of every
  worksheet, which was cosmetic while each comment line was its own paragraph. Grouping made it a
  correctness problem: the pragma sits immediately above the title in most worksheets, so the first
  paragraph came out as *"nomo 1 Complex numbers The imaginary unit is `i`…"*. It is hidden the way
  the trailer is — `Sheet::is_version_pragma`, an index test rather than a search, because only the
  first line can carry one — and it is hidden in **both** renderers, so the two agree on what counts
  as prose. Nothing else changes: still an ordinary comment, still parsed as one.
- **A worksheet that names itself is not titled twice.** `nomo html` passes the file stem as a title
  and emits an `<h1>` above the body. When the worksheet's prose opens with a level-1 heading, that
  heading names the document — it becomes the `<title>` and the chrome's `<h1>` is dropped. Only the
  opening block counts; a `# ` further down is a section inside the document, not a second name for
  it.

#### What it cost, measured against the snapshots

All 17 goldens moved and **nothing else did**. Every removed line is either a regrouped `<p
class="prose">` or one of the six `nomo 1` lines; every added line is a paragraph, or the `<ol>` that
`examples/interlock.nomo`'s numbered steps became. No computed value, no unit, no plot and no figure
changed, and `compare-targets.sh` still reports the 17 worksheets byte-identical between native and
WebAssembly. The text renderer was deliberately left alone except for the pragma: it is the
source-faithful format the golden suite diffs, and `# Title` reads as a title in plain text already.

#### What the examples turned out to be already

Every worksheet in `examples/` opened with a title line and a description on the line under it, so
grouping merged them: *"Cylinder volume The worked example from the design note."* The fix is the
feature — those sixteen title lines are now `' # Title`, and a level-1 heading at the top of a
worksheet is what names the document.

`examples/numerics.nomo` is the evidence that this was wanted before it existed. Its title was
underlined by hand:

```text
' Numerical methods
' ==================
```

A setext heading, written by an author who had no headings, in a file that predates this decision by
months. The underline is gone and the line above it is a `#`.

`examples/prose.nomo` is new, and is the worked example of the subset: every construct, the three
exclusions written out as a worksheet writes them, the backslash escape, and `<b>this</b>` arriving
escaped — with a cable-sizing calculation running through it so the prose has something to be about.
Its numbered steps have the mathematics between them, which is the `<ol start=n>` case in a real
document rather than a unit test.

Not decided here, and to be measured on its own: SMath's `Area` regions carry a title, which is a
section heading in the original document and would translate to `## `. That changes emitted prose,
so it moves the corpus baselines and belongs in its own commit.

### 8.42 Interpolation, read out of the numeric assembly (2026-08-29)

A worksheet reads engineering data out of a table — a property against a
temperature, a section against a depth, a measured curve against a load — and
the engine could not do it at all. Three questions decide what `linterp` means,
and the corpus can settle none of them: what happens **outside** the tabulated
range, what happens when the first column is not increasing, and what happens to
**units**. SMath 1.5 is on this machine, so all three were read rather than
inferred, the way §8.21 settled the plot span and §8.39 settled `·` between two
columns.

`TMatrix::Linterp(x, y, pnt)` in `SMath.Math.Numeric.dll` is four instructions:
refuse a table shorter than two rows (`Errors` 64), `buildlinearspline`, then
`splineinterpolation`. The answers are in the last two.

**Outside the table, SMath extrapolates — silently.**
`splineinterpolation` is the ALGLIB shape: `c[2]` holds the row count, a binary
search over the knots narrows `l`/`r` to one segment, and the value is Horner on
`x - c[l]` over four coefficients. There is **no range check anywhere in it**.
For a point below the first knot the search leaves `l` at the first segment and
the offset goes negative; above the last knot it leaves `l` at the last and the
offset overshoots. Either way the answer is the end segment's slope continued.

**An unsorted first column is sorted, silently.** `buildlinearspline` clones
both arrays and calls a private compare-and-swap over the pair before it builds
anything, so the caller's order is irrelevant.

**Units are dropped.** `TNumber::Linterp` calls `ToDouble()` on every entry and
returns `op_Implicit(float64)` — a bare number. The corpus shows what that costs
its users: the one dimensioned use in either corpus, `5.2-4.sm`, writes
`linterp(x.s/m, Q.s/N, x/m)*N`, dividing the units out by hand and multiplying
them back.

**Nomo differs on all three, deliberately.** Reading the implementation settles
what SMath *does*; it does not settle what this engine *should* do, and here the
two part company:

- **Units are carried.** Dimensional analysis is the product. The divided-out
  idiom above still evaluates unchanged — it is dimensionless arithmetic either
  way — so nothing that worked stops working.
- **Outside the table is refused.** A material table asked for a condition it
  never covered is exactly where a confident wrong number does harm, and this
  project's rule is that a construct which is right most of the time is worse
  than one that reports it cannot tell.
- **The first column must be increasing.** Sorting quietly repairs a table whose
  columns were passed the wrong way round, which is the mistake most worth
  seeing.

Each difference is a place where an imported worksheet could answer differently
from SMath, and each fails loudly rather than quietly, which is the only kind of
difference this importer is willing to have.

**What it cost, measured.** Registering the name let the emitter translate the
construct it had been refusing: `5.2-4.sm`, both editions, lost one import
marker each and gained the line `fn Q_int(x) = linterp(x_s/m, Q_s/N, x/m) N`.
No stored answer moved — those twelve were already failing on other constructs.

**And one correction to the registry.** `SMath.Manager`'s function-name table
holds `Linterp`, `Cinterp` and `Ainterp` and **no lookup function of any kind**.
`hlookup`, `vlookup`, `hmatch` and `vmatch` were in `builtins.rs` as SMath
built-ins on the strength of general knowledge; they are not. They come from a
plugin this installation does not carry, they are 18 calls in exactly one
worksheet — `SimplySupportedTimberBeam_Eurocode5_v1.0.sm`, a timber grade table
— and the registry now leaves them out, so the report calls them unknown. That
is the honest word: "SMath provides this and Nomo does not" and "nobody here
knows what this does" are different answers, and only the second is true.

They are therefore **not implemented**, and cannot be until their semantics can
be read somewhere: what a lookup returns when several rows match is exactly the
kind of question this project refuses to guess at. `cinterp` (8 calls) and
`ainterp` (3) are also left out for now — a cubic or Akima spline through a
material table overshoots between rows, and whether a worksheet wants that is a
design question with its own evidence to gather.

### 8.43 The loops that are left are programs, not folds (2026-08-29)

§8.38 and the roadmap both expected the remaining `for` loops to be
**recurrences and accumulators, which are folds** — expressible as `iterate` over
a pair once the language could carry one. Reading all eleven of them says
otherwise, and the expectation is withdrawn.

What is actually left, by the emitter's own classification:

| Refusal | Count | What the loops are |
|---|---|---|
| binds a whole name rather than an element | 9 | multi-statement bodies |
| body does more than assign | 6 | the same, seen from the other side |
| reads a name it is filling | 2 | a two-dimensional recurrence |
| reads names with no value here | 7 | upstream failures, not loop shapes |
| counter does not step by one | 1 | `range` with a step, still unverified (§8.7) |

And what those bodies hold, read one by one:

- **Hand-written Runge–Kutta**, in `RK4SingleEquation.sm`,
  `RK4SystemEquations.sm` and `RK4-2ndOrderODE.sm`. Each loop is a `line(…)` of
  a dozen statements computing K₁ to K₄ into local names and then advancing
  `ysol[k+1]`. That is a program with local temporaries and a recurrence in it,
  not a fold.
- **A tyre model** (`pacejka.sm`), two nested loops with eleven-statement
  bodies.
- **Divided differences** (`Newtoninterp.sm`, `Newtoninterpb.sm`): a nested loop
  filling `A[i, j+1] ← A[i, j] − A[i−1, j]`, which is a two-dimensional
  recurrence over a matrix being written in place.
- **One paired accumulator** (`Newtoninterpb.sm`):
  `line(z ← z·(α + j − 1)/j, yn ← yn + c[j+2]·z)`. This one *is* a fold — over a
  triple, because the body reads the loop counter as well as both accumulators.

Translating any of them needs one of three things this project has refused:
**local bindings inside an expression**, **indexed assignment into a matrix**, or
`iterate` over a **heterogeneous tuple** whose elements carry different
dimensions. The first two are mutation by another name (§ "A worksheet is a set
of definitions"), and the third is the vector-of-mixed-dimensions limitation
already recorded.

Even the one true fold is not worth the machinery. Emitting it means
synthesising `fn step(s) = [s[1] + 1, s[2]·(α + s[1] − 1)/s[1], s[3] + c[s[1]+2]·s[2]]`
and an `iterate` over it — correct, and unreadable, for one loop in one
worksheet. An import that produces something no engineer would keep has not
translated the worksheet; it has obfuscated it.

**The most useful observation is about the largest group.** Three of these
worksheets hand-write a fixed-step Runge–Kutta integration because SMath has no
such thing in its core. Nomo has `rk4` now (roadmap step 15). So their *intent*
is expressible here in one line — the importer simply cannot get there from
their *code*, because recognising a hand-rolled RK4 in a twelve-statement loop
body and rewriting it as a call is pattern-matching on a program, which is a
different and much less trustworthy kind of translation than anything else this
importer does.

The marker stays what it is: it names the construct, counts it, and leaves the
reader to write the two lines that replace it.

### 8.44 `at`, `description` and `cases`, measured (2026-08-29)

The roadmap ranked these three together as "the largest remaining non-CAS block"
— 140 calls. Reading them splits the block into three quite different things,
and only one of them is an importer question at all.

**`at` is SMath's substitution operator, and it is translated — and blocked.**
A worksheet in the mechanics corpus documents it in its own prose: *"local
values are substituted into variables without changing the variables in the
worksheet"*. The shape is `at(f, x ≡ v)`, with a **bare name** on the left — the
argument arrives through the substitution rather than as a call — so
`at(B, t ≡ t_max·s)` is what a worksheet writes where this language writes
`B(t_max·s)`.

That translation is now in the emitter, guarded twice: the name must be a
function this worksheet defines, *and* its parameter must be the name being
substituted. Without the second guard, `at(B, t ≡ v)` where `B` takes `u` would
silently answer a different question.

It gains nothing yet, and the reason is worth more than the gain would have
been. Of 31 substitutions across both corpora:

| | |
|---|---|
| into a name that is not a function here | 16 |
| whose right side is not `name ≡ value` | 8 |
| into an expression rather than a name | 7 |

The first group — the majority — is **§8.37 exactly**: the name being
substituted into is a formula-valued name, free in the variable, which this
importer deliberately does not infer. So `at` is blocked by the wall §8.37
already measured and reverted, not by anything about `at`. The refusals now say
which of the three cases each one is, which is what a coverage report is for:
before this they were all "the function `at`".

**`description` is not computation at all.** All sixteen regions that call it are
plot configuration — `XYPlot'Labels'YLabel : description(text)` and
`XYPlot'Traces#0'Name : description(text)`. What those worksheets are asking for
is **a labelled axis and a named curve**, which is a *plot feature this language
does not have* rather than a construct the importer is failing to translate.
Nomo names a curve after the function that drew it and labels an axis with its
unit. Ranked by the corpus, that is the most-wanted plot feature there is; it is
a language step, not an importer one, and it is written down here rather than
attempted under the heading of an import.

**`cases` is entangled with `ltle`.** Nine calls, and their conditions are the
`ltle`/`ltlt`/`lele` family whose boundary convention is still unverified
(§8.7 item 24). A piecewise function whose boundaries might be the wrong way
round is precisely the construct this project refuses to guess at, so `cases`
waits on that question rather than being answered ahead of it.

### 8.8 Strategy: corpus-driven

Build the importer as a separate crate emitting the Nomo document format, then run it across every
real worksheet you can collect and report statistics on unsupported constructs. That output
prioritises the work, doubles as the regression corpus, and gives an honest coverage number to
report to users. Never silently drop a construct — emit a visible unsupported marker in the output
document so a reviewer sees the gap. Pair it with the §8.2 result-comparison harness so coverage and
numerical agreement are measured together: 247 stored results are already available as assertions
before a line of Nomo exists.

## 9. Testing strategy

**Adopt CalcpadCE's rendered-output regression discipline on day one.** It is the single best idea
in either codebase. Every example worksheet is rendered and diffed against committed expected
output; any change to calculation or rendering fails CI until the expected output is regenerated, so
behavioural change always appears in the diff next to the code change that caused it. This is what
makes an engine safe to refactor.

Two deliberate improvements over CalcpadCE's version:

1. **Bit-exact comparison, no numeric tolerance** (see §3). Their tolerance is a workaround for
   nondeterminism this design eliminates.
2. **Snapshot the full rendered trace**, not just final values (see §5).

Also worth copying: a denylist mechanism for genuinely nondeterministic examples — though with this
design the only legitimate sources are time, randomness, and user input, all of which should be
injectable and stubbed rather than denylisted.

## 11. Open questions

1. **Numeric model** — resolved in §3, but the choice of math library (Rust `libm` versus a
   correctly-rounded implementation) is still open and can be deferred behind a trait.
2. **Affine units** — forbid in arithmetic, or flag and handle? Needs a decision before operators
   are written (§4).
3. **Is `rad` dimensionless?** And how are logarithmic units handled (§4)?
4. **May users declare new base dimensions**, or only derived units?
5. **Plotting library** — deferred. Prefer something small (uPlot, Observable Plot) over Plotly.
6. **Local file storage** — File System Access API versus IndexedDB versus both. Note the API's
   browser support is uneven, which matters given EP's cross-browser constraint.
7. **Which browsers and platforms are actually required?** EP commits to Chrome, Safari, and
   Firefox on desktop *and* mobile, plus correct browser printing. That is a demanding constraint;
   decide deliberately whether to inherit it.

Importer-specific, ranked by risk:

8. ~~**Did the `.sm` format change between 0.98 and current 1.x?**~~ **Resolved: yes, structurally**
   — new root element, XML namespace, new payload and result kinds. Measured against a second,
   1.3–1.5 corpus in §8.10. What replaces it: **how much else changed after 1.5**, and the answer to
   that is the same as before — get the worksheets the users being migrated actually hold.
9. **What is the `—` operator?** 6 uses in the wiki corpus. Re-measurement narrows it: every use has
   a function call on its left and that function's expanded form on its right, which reads as a
   **symbolic-evaluation display** rather than a binding — if so, those six right-hand sides are
   stored answers for the oracle (§8.11). Confirm against SMath before implementing. `|` is settled
   (logical or, all 3 uses in `if` conditions, §8.11) and `†` is the cross product (§8.10 finding 5).
9a. ~~**What does an import do with a CAS worksheet?**~~ **Resolved (§8.12).** The target user is
   the practising engineer doing dimensioned calculations, so no CAS, and the 7.7% of regions that
   need it become visible markers. What replaces it, parked rather than open: **is exact linear
   solve over symbolic coefficients ever worth adding?** What two thirds of the mechanics corpus
   exercises — but justified only by the target user's own files, and **no longer described as
   bounded**: §8.40 measures the layers, finds the cheap ones cheap, and finds this one gated on a
   pivot zero-test that is decidable only over an exact coefficient field.
9b. **Which language does an import keep** when a worksheet carries all of them? The trilingual
   edition holds ger/eng/rus in the same file (§8.9, §8.10).
10. **Does Nomo's own syntax expose global definitions**, or does it only reconstruct SMath's `≡` on
    import? The engine must represent them regardless (§6), but the surface syntax is a separate
    choice.
11. **How much of SMath's function surface is in scope for v1?** The wiki corpus gives usage counts
    to rank by; `el` alone accounts for 454 uses. The 1.x corpus adds a second axis — 147 names, 79
    of them defined in-document — and shows the plugin ecosystem is part of the surface too (§8.10).
    Decide a coverage target rather than discovering it.
12. **Licensing of the corpus** if it is ever committed to a public repository (`corpora/nomo-corpus/README.md`).

**Verified by cross-building and running (2026-08-26)** — the cross-architecture half of §3,
which until now was argued from the specification rather than measured. The engine was built for
`aarch64-unknown-linux-musl` and the nine-worksheet corpus rendered under `qemu-aarch64`: output is
